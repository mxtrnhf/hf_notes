## 1. The part/module info text (`FUN_1400211a0`)
* `FUN_1400211a0(Body* part, owner, char flag)` (`0x1400211a0`..`0x140023575`, no direct callers: a virtual method) builds the **part description tooltip**: a GUI element (`GUI_2`, size `0xed0`, style `"gui_mil"`, text set with vtable `+0x370`, linked to the part at `+0x9c8` and to the global `0x1403eef70`) with the title (part name, `displayOnUI_`), the description (`displayDescriptionOfPart`), `DAMAGE_STAT` ("damage: N%", from `part+0x2c8 / +0x2cc`), then stat lines (`PRICE_STAT`, `FIREPOWER_STAT`, `FIRE_RATE_STAT`, `CLIP_AMOUNT_STAT`, `THRUST_STAT`, `POWER_STAT`, `POWER_NEED_STAT`, `FUEL_NEED_STAT`, `FUEL_STAT`, `AMMO_NEED_STAT`), a contamination sign (`{animation=sign_contamination_big}`) and the radiation damage line `GAME_DMG_RAD`.
* **Colours are markup strings, fixed, independent of the side**: title `{font=dinpro_20_black}{align=2}{color=4293056435}` (`0xFFE2D7B3`, beige); body text `{font=dinpro_14_med}{align=0}{color=4293056435}`; price / firepower labels `{color=4294965760}` (`0xFFFFFA00`, yellow); the other stat labels `{color=4294967295}` (white); tutorial hint `{color=4287413225}`; radiation `{color=4293706790}`. Strings are in `.rdata` at `0x140353f28`..`0x140354090`.
* This is hover/inspection text for a module, **not** a per-ship callout drawn around the hull. I did not identify a per-ship, always-on callout renderer in battle (no function that loops over ships and prints module hints near the hull); the user's "generator / escape pod / destroyed module hints" may be this tooltip or the radio/event lines (`radio_lost_generator`, `REACTOR_DESTROYED`, `ESCAPED_HINT`, which are dialogue/UI strings, not hull overlays). A screenshot of the exact element would settle which one.

## 2. The game's friendly / hostile palette (found)
`Sprite::SetColor`-style calls take an ARGB constant built with `FUN_140016fe0(&col, ARGB)` / `0x140172ae0(sprite, ARGB, corner)`. The pair used for side colouring in the result screens:
| meaning | ARGB | decimal (for `{color=N}`) | seen in |
|---|---|---|---|
| **friendly / player side (cyan-blue)** | **`0xFF00E4FF`** (R 0, G 228, B 255) | **4278248703** | `afterBattleStars??` `0x14029fc1c` (selected when the side value is 2), `FUN_14029b3e0` (8 uses, `0x14029b723`..`0x14029bc60`), `handleLandingGUI?` `0x1402a16a2` |
| **hostile (red)** | **`0xFFDD2727`** (R 221, G 39, B 39) | 4292419367 | `afterBattleStars??` `0x14029fc5f`; **`creatureLogic` (guided-missile logic id 1 setup: the `sign_enemy_s`, `sign_missile_enemy`, `sign_dir` FX sprites, `0x140044457`, `0x14004497b`, `0x1400449e1`, `0x140044c61`)**; `displayLables` / `mainMap` / `handlePauseUnpause` (map and pause marks) |
The `afterBattleStars` pair is a vertex-colour pair for result-screen sprites: `CMP R13D,2 / JNZ / MOV EDX,0xff00e4ff / CALL 0x140172ae0(sprite, ARGB, corner)` then `CMP [rbp+8],2 / MOV EDX,0xffdd2727`. So **if the user's "nice blue" is the game's own side blue, it is `0xFF00E4FF`**.
**Not found:** the code that tints the small plane icons in the live combat view, and whether friendly missiles/planes get `0xFF00E4FF` or a different blue there. In `creatureLogic`'s missile setup the immediate is the hostile red; the friendly branch does not use an immediate (probably a sprite whose texture is already blue, a colour table, or the other branch of the same call). The `sign_craft_friendly` / `sign_missile_friendly` / `sign_friendly` sprites (`0x14035f090`, `0x14035f068`, `0x14035a340`) are used only by `renderMissilesOnMap` (the strategic map's air/missile markers) and have the colour baked into the sprite sheet (no tint immediate near them in what I read).
**Cheapest way to settle it live:** hook the colour setter `0x140172ae0` (RCX sprite, EDX ARGB, R8D corner) and `0x140016fe0` (RCX out vec4, EDX ARGB) during a battle with own planes airborne and log the distinct ARGB values with the caller return address; the plane-icon value will be the one that appears only while planes are up.
