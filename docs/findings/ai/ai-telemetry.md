# Battle telemetry for AI research (`hf_ally` v0.12.3 to v0.12.7)

Status (2026-10-18): **v0.12.4 to v0.12.7 have run in game** (several captures, no crash, no `TELEMETRY BUG` line, the user reports no lag with the per-frame body scan; no frame profiler exists, so "no lag" is the user's observation only). Installed now: `hf_ally_v0.12.7_debug_telemetry.dll`. Source: `hf_ally/src/telemetry.rs`, behind the cargo feature `telemetry` (a plain or `megalog`-only build contains none of it). Tags: legend in `../../README.md`.
Purpose: the harness of "Where to take the AI" stage 3 in [battle-ally.md](battle-ally.md): record how the player flies and what the enemy AI does, so hand-built tactics can be tuned from data (design and decisions: [ai-hf-ai-design.md](ai-hf-ai-design.md)). Read-only: no game memory is written and no game function is called. Page-checked reads (`diag::rd`) everywhere except the per-frame body scan, which uses plain reads of the bodies in this frame's array (the game walks the same array).

## How to run it
* Config `Modloader/config/ally.json`: `"telemetry": true`; `"spawn_ally": false` gives a solo capture (the battle-manager hook is installed when `spawn_ally` OR (feature `telemetry` AND `telemetry`) is on). F9 drops an optional marker row; not needed.
* Output in `Modloader/logs/`, one set per battle (since v0.12.6): `hf_ally_telemetry_<unix>.csv`, `hf_ally_parts_<unix>.csv`, `hf_ally_bodies_<unix>.csv`. Unbuffered; a crash loses nothing. Send all three plus the newest `Highfleet_*.log` and `hf_ally_megalog_*.log`. Never commit them.
* `python3 hf_ally/tools/telemetry_summary.py hf_ally_telemetry_<unix>.csv`: speed, range bands to the nearest armed enemy, buttons / boost time, flares, rounds, Zenith drops, and an aim report (aim error to the nearest armed enemy while firing and not, cursor offset, sweep speed); warns when a row's field count differs from the header.
* `python3 hf_ally/tools/telemetry_damage.py hf_ally_parts_<unix>.csv`: per ship the parts seen, name strings, health lost per second (works on real data).

## Files and columns
**`hf_ally_telemetry_*.csv`**, about 10 rows per game second per live ship. `P` = the ship the player flies (live, role `+0xd70 == 1`, AI flag `+0xbd4 == 0`), `E` = every other live creature (friend, foe, neutral), `M` = F9 marker. Columns: `t` game clock, `kind`, `id` (P is 0), `side` (`+0xad4`, negative = enemy), `state` (`+0xbdc`), `x,y` (`+0x1840/+0x1844`), `target_id` (-1 unknown, 0 = the player), `gun_*` / `zen_*` / `fl_*` (count, loaded sum, reserve sum of the lists at `+0x1360`, `+0x13d8`, `+0x1408`), `parts_n, parts_alive, hp_sum, hp_max0`, `fuel, fuel_cap` (`+0x1638`, f64), `crew, crew_cap` (`+0x17ec`), `aggr` (`+0xbc4`), `retarget` (`+0xb28`), `wp_x, wp_y` (the AI waypoint `+0xbf0/+0xbf4`), `launch_cd` (`+0xd60`), `mode` (`+0xb48`), `role` (`+0xd70`), `ai` (`+0xbd4`), `reach1, reach2` (`+0x1838/+0x183c`), `rp_*`, `cr_*`, `f0..f4` (control bytes `+0xbbc..+0xbc0`), `ammo_flags` (hex of `+0xc74..+0xc7e`), `name`. Player only: `boost` (`+0xba8`), `lmb, rmb` (`GetAsyncKeyState`), `mx, my`, `amx, amy`, `zoom` (`0x1403c11cc`), `vc0..vc7` (8 floats at `0x1403c0dc0`), `wave_t` (`0x147fc7020`), `ctl` (hex of `+0xba0..+0xbe0`).
**`hf_ally_parts_*.csv`**: `S` a part seen (`oid`, stats index, state, health, max health, local x,y), `H` health or state changed (the damage log), `L` part left the ship's list, `N` per ship: every MSVC `std::string` found in the creature object as `offset:text|...`. Columns `t,kind,ship,part,oid,stats,state,hp,hp_max,lx,ly`.
**`hf_ally_bodies_*.csv`**: `N` a flying body appears (first frame its pointer is seen), `X` it is gone (last position and velocity read the frame before, roughly the impact or expiry point), `K` bodies of constant kinds listed once at the start, `C` per sample counts by logic id (`id:count`), `B` 10 Hz track of a body with a target link (cap 80 per sample, shells count against it). Columns `t,kind,logic,stats,body,x,y,vx,vy,hp,ttl,target_id,owner_id,owner2_id,oid,counts`. Positions in world units, velocity units per second.

## Addresses and what they mean (1.163)
* **Ship design name:** a `std::string` at Creature `+0xa90` [game]: the `N` rows of five enemy ships read `Paladin Mk2`, `Gladiator`, `Nimrod`, `Kormoran`, `Navarin`. The player's ship reads `TestProject` although the user calls it Lightning: the name is the file/design name, so for the player's ship the offset is **confirmed only as "a name string", the meaning is open**.
* **Whole-ship part list:** Creature `+0x1330` (begin) / `+0x1338` (end), 0x18-byte entries, Node at `+8` [code: the loop in `CalculateStats` `0x14007fcf0` calls `0x140071380` per part of class code `0xf`; game: 88 parts for the player's ship per battle]. Part health `+0x2c8` current, `+0x2cc` max (`calcDMGPercentage` `0x140048410` is exactly their quotient) [code], part state `+0x48` (0 = dead or dropped), `oid` string at part `+0x190` [game]. `hp_sum` / `hp_max0` are sums of these per-part numbers, NOT a game "ship health" (there is no single field).
* **Per-category vectors** that `0x140071380` fills (read from the decompilation, names are [guess], unverified except where noted): `+0x1348` power producers, `+0x1360` weapons ([game]: `gun_n` 2 and 2 x 19998 reserve for a ship with 2 x `MDL_CANNON_100_2`), `+0x1378` fuel tanks, `+0x1390` engines, `+0x13a8` / `+0x13c0` two gun groups, `+0x13d8` Zenith ([game]: `zen_n` 8 on Zenith ships, drops as racks launch), `+0x13f0` a second launch list, `+0x1408` flares ([game]: empty on the player's ship), `+0x1420` parts with flag `0x2000000`, `+0x1438` bombs, `+0x1480` crew, `+0x1498` sensors, `+0x14f8` legs.
* **First part of the part list = the ship's physics** [game]: its `+0x130/+0x134` matched the position difference dx/dt in 1491 of 1493 samples, `+0x138` is the heading in radians (range -1.6 to 3.8 seen, not wrapped). Creature `+0x130..+0x138` read 0 always. Heading does NOT follow the aim.
* **Player ship identity** [game, user + parts log]: 2 x `MDL_ENGINE_05` and 4 x `MDL_ENGINE_04` in the parts log match the user's 2 x D-30S and 4 x NK-25, and 2 x `MDL_CANNON_100_2` match `gun_n` 2.
* **Fire byte** [game]: `f0` (`+0xbbc`) was on together with LMB in 24 of 25 samples; `f1` (`+0xbbd`) never lit for the player. **Resolved 2026-10-18 [code + game]:** the decompiled `FUN_14007eb50` fires the list at `+0x13a8` when `+0xbbc` is set and the list at `+0x13c0` when `+0xbbd` is set (weapon group 0 = LMB, group 1 = RMB; the group is the part's field at +0x7a4, which also picks `reach1`/`reach2` = `+0x1838`/`+0x183c`). Over all v0.12.x captures `f0` (+0xbbc) was on in 1736 of 1741 LMB-only samples and `f1` (+0xbbd) lit only in the 2 samples where RMB was held together with LMB. `structures.md` and `flare-crash-hunt.md` were wrong and are corrected; `ai-flares.md` was right.
* **Aim signal** [game, four session files from several battles]: floats at `0x1403c0dc8` / `0x1403c0dcc` (`vc2`, `vc3`, range -100 to 100, continuously changing) are a **world-aligned aim offset**: `atan2(vc3, vc2)` (y not flipped) pointed at the nearest armed enemy while firing with median error 3 deg, 83-84% within 10 deg, 93-96% within 30 deg (concentration 0.95); not firing: median 9-14 deg. Cursor offset averages 84-93 of 100; aim sweep median 2-8 deg/s, 90th percentile 36-48 deg/s. `vc0, vc1, vc4..vc7` and `wave_t` (`0x147fc7020`) were constant; `cr_*` always 0.
* **HGE mouse `+0x9fc/+0xa00` in battle** [game]: single-axis values -1 / 0 / 1 (one axis non-zero at a time), `amx, amy` about +-5 per sample. Real mouse deltas would vary and often be 0, so "mouse delta" is [guess, contradicted]; "held direction keys" is [guess, untested]. Not an aim source.
* **Global body array** `0x143a33c90` (`Body*`), count u32 at `0x143a51150` [code, walked by `FUN_14002f480` and qol `ai_flares`]. It holds projectiles AND constant bodies: logic ids 0, 200, 400, 910, 3506 with counts 82, 14, 20, 64, 1 that stayed fixed while ships lost dozens of parts, so they are not ship parts; "level props" is [guess]. Projectile logic ids seen: 100 shell, 160 proximity shell, 1 missile (`MDL_MISSILE_01`, stats index 130; **logic id (`+0x3c4`) and stats index (`+0x188`) are different fields**), 550, 700, 900, 210 (not identified). Fields: owner `+0xb8`, target-link pointer `+0x498`, launcher-link pointer `+0x4b0`, time to live `+0x2c0`.
* **Body owners and targets** [game, battle `1792281962`, 26 s]: 104 shell births, 103 deaths; **49 shells have the player as owner against 51 rounds spent** (so `+0xb8` resolves the firing ship), the enemy ship 3 fired 55. `owner2_id` equals `owner_id` for shells. **For shells `target_id` equals `owner_id` in all 104 births: the target column is meaningless for shells**; it is a real target only for guided bodies. The missile's owner stays unresolved (-1) both ways; its target resolves to the player.
* **Session handling**: the battle-manager roster does not always empty between battles (three battles shared one CSV set in v0.12.4, which made the player's parts look tripled: 88 parts per battle, re-created each time). v0.12.6 opens a new set when the player's ship pointer changes or the clock jumps by more than 2 s.

## What the captures show (one pilot, Lightning, solo)
* [game] First files (v0.12.3, 31 s and 312 s): well formed; every enemy targeted the player the whole time; three enemies per wave starting 1500-2800 away; nearest armed enemy median 340-520 units, 53-59% of the time under 500, closest 77-160. Fire buttons held 58 s and boost 32 s over the 312 s file, no flares.
* [game] Later files (v0.12.4, four sessions of 36 s, 38 s, 160 s, 204 s): the player's summed part health went from 6600 to 2567 in the long fight; enemy ships lost 800-3500 part health each. Enemy Zenith racks went 8 to 0 within about 35-65 s of a battle. That emptied rack means "launched" and that it is the `ai_missile_dump_chance` patch (installed `qol.json`: 0.7) are [guess]; the bodies file now carries the missile births to settle it.
* **Missile overshoot test** [game, weak]: 72 missile tracks (logic 1) aimed at the player from four v0.12.4 sessions, 10 Hz tracks. 8 hit (damage within 0.4 s, closest approach about 62 units; player sideways speed 1 s before closest approach, median 81), 25 near misses under 120 units without damage (97), 39 passed 120 or more away (137). More sideways speed before the approach went with fewer hits, as the user expected ("let them overshoot"). Caveats: the `B` cap of 80 rows per sample is shared with shells and can cut tracks, "hit" counts any player damage within 0.4 s (shell hits too), 10 Hz positions, small sample from few battles. The per-frame `N` / `X` data of v0.12.7 allows a clean redo.

## Known defects and unknowns
1. `telemetry_summary.py` max speed is inflated by position jumps between battles in files from before v0.12.6; rounds are over-counted when guns reload (use endpoints); `zen_n` drops cannot tell "launched" from "shot off".
2. The camera / world position of the cursor is not needed any more (`vc2/vc3` gives the aim direction) but the offset's units (screen fraction?) are unknown.
3. Unknown: logic ids 550, 700, 900, 210; the missile's owner field; flare `loaded` / `reserve` semantics; what `f1` is; whether the `B` cap loses missile tracks.
4. Cost: `diag::rd` calls `VirtualQuery` per field; the user saw no lag, nothing was measured.
