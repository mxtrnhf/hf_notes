# Player keys to engine commands, the swivel servo, and the engine overheat lockout (v1.163), ghidra-miner, 2026-10-21

Tags: **[V]** read in the 1.163 program (decompile + disassembly, constants read from memory), **[log]** measured on logged flights (Kormoran 1792599418/488/579, Gladiator 1792599652, hook N/S/G rows), **[open]** not resolved. Names: `Player_SendThrustCommands` `0x1402a9300`, `vectorCalculateAngles_` `0x14000dda0`, `Part_HandleCommand` `0x1400533f0`, `Engine_ServoUpdate` `0x140053690`, `Engine_ApplyThrustForce` `0x140028360`, `Part_Tick` `0x140054fb0` (vtable +0x1e0), `Body_ThermalStep` `0x140055870` (vtable +0x1f0), `CreatureUpdate` `0x14007eb50`.

## 1. From keys to the command angle [V]
Per player and tick (`Player_SendThrustCommands`, only if `time_related_global_ != 0`):
* `a` = hull angle (root `+0x138`), wrapped to `[-pi, pi]` (`x - round(x/2pi) * 2pi`, then folded). `h = (sin a, -cos a)` (hull "forward", the direction a part at angle `a` pushes).
* `m` = the move vector of the player's input record (`+0x10/+0x14`; (0,0) if none non-zero). Key S alone gives `m = (0, +1)` as you logged.
* Two flags from the input record: `+0xe3` (**this is Q**) and `+0xe2` (**this is E**). Evidence [log]: with Q held, bank 1 (parts with codes {100, 102}, e.g. part 169) is commanded `a + pi` and bank 2 (codes {101, 103}, part 173) is commanded `a`.
  * start `v1 = v2 = m`
  * flag `+0xe2` (E): `v1 = m + h`, `v2 = m - h`
  * flag `+0xe3` (Q): `v1 = m - h`, `v2 = m + h` (applied after the E step, so both flags together cancel to `m`)
* Angle: `vectorCalculateAngles_(v)`: **if `v == (0,0)` exactly the angle is 0.0**; else normalise (`v / |v|`) and return `atan2f(x', -y')` with `x' = v.x/|v|`, `y' = v.y/|v|` (first argument x, second argument -y; note the game writes it as `atan2f(y*0 - x*(-1), x*0 - y*1)`). Range `(-pi, pi]`. Angle 0 points the thrust at `(0,-1)` (up), a part at angle `c` pushes along `(sin c, -cos c)`.
* **Signed zeros do not matter**: the first argument is `y*0.0 - x*(-1.0)` which is `+0.0` for `x = +-0, y = 1` (checked both signs), so **`m = (0,+1)` (key S) gives exactly `atan2f(+0.0, -1.0) = +pi` (float 3.1415927)**, never `-pi`. The swing through `-pi` comes from the servo wrap (section 2), not from the angle.
* Sent every tick (each part checks its own command list, `Part_HandleCommand`): code 100 = angle v1 (bank 1 servo), 0x65 (101) = angle v2 (bank 2 servo), then (unless `v1 == v2 == (0,0)` and neither flag is set, in which case the function returns before sending) 0x66 = angle v1 + strength, 0x67 = angle v2 + strength. Strength = creature `+0xba8`.

## 2. Servo error and motor [V]  (`Engine_ServoUpdate`, command 100/0x65 ONLY)
```
wrap_pos(x): n = floor(|x| / 2pi + 0.5); k = n if x >= 0 else -n; r = x - k*2pi; if r < 0: r += 2pi     # [0, 2pi)
c = wrap_pos(cmd_angle)            # cmd +4
p = wrap_pos(part +0x138)          # the PART's own angle only; the hull angle is NOT subtracted here
d = c - p
d = d - k*2pi  with  k = sign(d) * floor(|d|/2pi + 0.5)          # same rounding rule: result in [-pi, pi]
```
* **Tie rule**: float `pi` is exactly half of float `2pi`, so `|d| = pi` gives `floor(0.5 + 0.5) = 1`, i.e. `d = +pi` becomes **`-pi`** and `d = -pi` becomes **`+pi`**. Key S with the part at angle 0: `c = pi`, `p = 0`, `d = +pi` becomes `-pi`: the engine swings through `-pi` (your logged -2.23 ... -4.48). For an `E/Q` bank commanded `a +- pi` the sign of the swing is decided by the float value of `a`: `v = m - h = (-sin a, cos a)`: `a` tiny positive gives `c = -pi + eps`, `c' = pi + eps`, `d = pi + eps` becomes `-pi + eps` (swings negative); `a` tiny negative gives `c = pi - eps` which stays `+pi - eps` (swings positive); `a == 0` exactly gives `+pi` and `-pi` as for S. So replicate it in float32 with the wrap code above and the swing direction comes out right.
* Motor: if part power `+0x818 != 0`: `speed = d * P * Stats+0x108 * P` (`P = +0x818`, 1.0 in the logs; `Stats+0x108` = m_mdl_rotation, default 3.0; **x0.25 if the arcade flag `0x147fc6fd4`**), max torque `+0x1d8 / 100` (the part mass / 100), via `Joint_SetMotor` on each joint in the part's joint list `+0x230`. **It is linear in `d`: no sqrt, no dead zone.** (The `sqrt`-with-0.01-dead-zone servo `P*Stats108*P*sign(d)*sqrt(|d|)` at `0x140053870` is command **200**, it targets an owner position and is not used by the engines; my earlier coupling note attached it to the engines by mistake and is corrected.) The servo writes `d` back into the command record (`+0x10`), which is only bookkeeping.
* `Part_HandleCommand` runs a handler only if the command code is in the part's own list (exact match) and the part is active (vtable `+0x78`).

## 3. Strength, boost, ramp [V + log]
* Strength `creature +0xba8`: **1.0 by default** (set at creature creation `0x140072d1f`), **2.0 while Shift is down**, back to 1.0 on release (key handlers `0x1401896a0` writes 2.0 at `0x14018980d` if `dt != 0`; `0x14018a530` writes 1.0 at `0x14018a76b`). **A step, no smoothing.** In the telemetry `ctl` blob this is the float at byte offset 8 (2.0 at 18.62, 1.0 at 19.46, 2.0 at 21.52, 1.0 at 28.32 in 1792599418).
* Force per engine call: `F = Stats+0xf8 (GetThrust) * strength * g * (1.2 if perk 2) * (0.01 if +0xbc4 < 0.5) ...`, `g = cos(cmd_angle - part_world_angle)`, **no force if `g <= 0`** (so under Q the bank-1 static engines, which point along `h`, never fire: their command is `a + pi`, `g = -1`; part 82/145 keep +0x840 = 0 in the logs).
* `creature +0xbc4` ("spool"): updated in `CreatureUpdate` (`0x14007ef90..0x14007f089`): with total thrust `+0x17fc + +0x1800 != 0` it rises by `dt / D` per tick (`D = 30` here: the flags `0x147fc6fb7/f82/fd4` branch; 10 s in a plain campaign battle, 120 s for another flag set; measured +0.00067 per tick), clamped at 1.0; with zero thrust it falls by `dt / XMM12` (measured -0.002 per tick = dt/10), floor 0, but the decrement only applies while `v + dt/10 > 0.55` so a ship that has once reached 0.55 never drops below about 0.55. **The only effect is the `x0.01` thrust penalty below 0.5**, which a running ship does not reach (log: 0.80 to 0.84 at the Kormoran hold). So the ramp can be ignored except right after spawn (+0xbc4 starts at 1.0 in the AI/player setup, so effectively never).

## 4. Everything that stops an engine's force [V]  (`Engine_ApplyThrustForce`)
In order (each makes the call return with **no force and no sum update**):
1. `+0x818` (power) `== 0`; 2. `+0x848 != 0`; 3. owner is not a creature; 4. `g = cos(cmd - angle) <= 0`;
5. **`+0x2ec >= 500.0` (part temperature): write `+0x810 = 3.0` and return**; 6. **`+0x810 != 0`** (lockout timer); 7. (AI ships only) another engine of the same ship within 3 units with `+0x810 != 0` ... skip; 8. fuel: the player's fuel burn returns 0 although the burn is not 0.
Otherwise: force applied with `Body_AddForceAtPoint` at the part centre (`+0x210/+0x214`); `+0x2f0 += (g*strength)^2 * 70 * dt` (heat dose, `70.0` read at `0x140354844`); `+0x840 = F * 1e-8 + 0.5` (flame size, NOT a gate: it keeps its last value while the engine is locked, which is why the logger's "engine activity" looks flat at 2.27 and dips to 0.7 - 1.1 for the static engines); the bank sums `+0x17fc/+0x1800` (+ Fx, Fy) are increased by `F`.

## 5. Engine temperature and the lockout [V + log]
* **Who steps the temperature, with what arguments [V]**: `0x140127810` (renamed `World_ThermalPass`, called once per frame from `SomethingGameTask` at `0x1401275d7`): `n = ceil(dt / 0.2)` sub-steps (n = 1 at 50 Hz); for each active body in the global body array (up to 15000): `Body_ThermalStep(body, dt_step = (dt / n) * 4.0, heat = 1.0 / n, ambient = 0.0, k = 200.0)` (k is the immediate `0x43480000`). **Thermal time runs 4x faster than game time.** Afterwards every active body gets its dose `+0x2f0 = 0` (so the dose is a per-frame input, not a store). `FUN_14011da20` (renamed `Container_ThermalPass`) is the same call over a container's body list (+0x100, 3000 max) with caller-supplied args and also zeroes `+0x2f0`; its callers are data-only (vtable), not needed for combat engines.
* `Body_ThermalStep`: `T(+0x2ec) += (k * 5.9523813e-5 + 1/120) * (ambient - T) * dt_step + heat * dose(+0x2f0)`, then conduction `(T - Tn)/10 * dt_step` to cooler joined bodies in the slot vector `+0x350` (at most 100), then `Body_BurnUpdate` (ignition at Stats `+0xbc`, fire damage). With the arguments above, per 50 Hz tick: **`T += -0.0016191 * T + dose`** (0.0202381 * 0.08), time constant 12.4 s. Dose sources: `Engine_ApplyThrustForce` (`(g*strength)^2 * 70 * dt` per call = 1.4 per tick at g*s = 1, 5.6 at g*s = 2), `Body_AreaDamageFromBlast` (blast fire), `Part_Tick` drains it into the burn terms.
* **Predicted trip time (isolated engine, T0 = 0, no conduction)**: g*s = 1: equilibrium 865, T = 500 after 10.6 s; g*s = 2 (Shift): equilibrium 3459, T = 500 after 1.9 s. Check [log, 1792599418]: Shift down at 21.52 after ~2 s at s = 1 (T about 130): trips at 22.70 (static 147), 22.82 (static 84), then 23.28/23.32 (RD-59, lower g because the swivel lags: dose is quadratic in g). Matches within 0.1 s. Conduction looks small for these engines (not needed to match), but the neighbour graph is not decoded [open].
* Lockout timer: `Part_Tick` does `if +0x810 != 0: +0x810 -= dt` (floored at 0): measured on the log, set to 3.0 and counted down by exactly 0.02 per tick [log, part 84: 2.98 at t = 22.82, 2.10 at 23.70]. While `T >= 500` it is re-armed to 3.0 on every call, so a lockout lasts 3.0 s from the last hot call (3.2 to 3.5 s in 1792599488/579; the Gladiator flight never overheats).
* Under Q + Shift the dose is `(1*2)^2 * 70 * dt = 5.6` per tick per engine (4x the Shift-less value), so the engines reach 500 within about a second or two of boost: Kormoran 1792599418 (Shift down at 21.52): static 147 trips at 22.70, static 84 at 22.82, RD-59 169 at 23.28, RD-59 173 at 23.32; again 24.80 (84), 25.06 (147), 25.86 (173), 25.90 (169); 28.30 (147/84), 30.88 (169/173)... The statics (3.2e7 thrust, 1.5e7 m_at) trip before the RD-59 (9e7 thrust).
* **Effect on the thrust the simulator compares**: bank sums in that window (S rows `+0x17fc/+0x1800`): 1.8e8 / 3.08e8 (everything firing), 1.8e8 / 2.44e8 (22.68, static 147 out), 1.8e8 / 1.8e8 (22.8, 84 out), 0 / 1.8e8 (23.28, 169 out), 0 / 0 (23.30 to 23.70, all out). Stabiliser consequence: with a bank idle (`+0x17fc == 0 or +0x1800 == 0`) the stabiliser runs with `Ta = 0` and `Tw * 0.5` (all-out ticks: T = 3.35e7 per RD-59 call instead of 6.7e7 at w = -0.31). Hit points also drop in bursts of about 3.6 per 40 ms at 20.8 - 21.9, 24.1 - 25.1, 31.9 - 33.0 (burn damage once the temperature passes the ignite value) [log, telemetry hp_sum].
* **Apply to the sim**: replay `+0x810` of the N rows as an input mask (engine force is zero while `+0x810 != 0`), exactly like the fuel cut; check whether the Kormoran w then saturates at about -0.4 instead of -1.0 (real thrust average drops about 12 to 25 % and the static engines' share of the couple drops with them). ## 7. Conduction rule and the fire extinguisher (added 2026-10-21, later) [V]
**Conduction (`Body_ThermalStep` `0x140055870`, exact)**. After the decay and dose update of the body's own temperature `T` (`+0x2ec`):
1. Build a list (static array `0x1403c63d0`, at most 100) from the body's slot vector (`+0x350` .. `+0x358`, 8-byte entries, filled from the object property **`m_slots`** at load, `bodySecondaryInit` `0x140027387`): for each non-null entry take the body `nb = entry->+0x58`; keep it only if `nb != 0`, **`nb.T <= T and nb.T != T` (strictly cooler)** and its mark `+0x220 == 0`; set `+0x220 = 1` and append.
2. For each kept neighbour, **sequentially**: `flow = (T - nb.T) / 10.0 * dt_step`; `T -= flow`; `nb.T += flow` (the neighbour gains exactly what the body loses; `T` is the already-updated value, so later neighbours see the reduced `T`); clear `nb.+0x220`.
3. `dt_step = dt * 4 / n` (the same as the decay term; 0.08 at 50 Hz), so **each strictly cooler slot neighbour takes `0.008 * (T - nb.T)` per tick** (about 0.8 %/tick of the difference).
Heat only flows downhill from the body that is being stepped; every active body is stepped once per frame in global-body-array order, so a hot body feeds its cooler neighbours when it is stepped, a cooler body never pulls. "Joined" means: listed in the body's `m_slots` data with a live occupant body at `slot+0x58` (the module slot graph of the ship design, not Box2D joints), so whether a swivel engine conducts to its frame depends on the slot list of that engine's object data (the sim can read it from the `Objects/*.seria` of the module: property `m_slots`). Compare with your fit: `0.0055/tick toward 30` is one slot neighbour at about 0.7 x the rate; with N cooler neighbours at temperatures `Tn_i` the loss is `0.008 * sum(T - Tn_i)`, and the neighbours warm up (they are not an infinite sink: at 5-44 they gain heat and the engine side is then cooled less, they in turn leak to their own cooler neighbours).

**What writes 100 into every engine at 23.72 / 26.22 (1792599418): the fire-extinguisher action.** `rep_140033220_LoadParticle?` `0x140033800` (renamed `Part_ExtinguishNearbyEngines`) is called on one extinguisher module (`R14`): for every engine in the owner's engine list (`+0x1330..+0x1338`, 0x18-byte records, part pointer at `+8`) whose position (`+0x964/+0x968`) is within **30.0** units of the module (`0x1403524dc`; d^2 prefilter < 10000): **`T(+0x2ec) = 100.0`, dose `+0x2f0 = 0`, lock `+0x810 = 0`** (the store at `0x140033946/0x140033951`, a qword write that also clears `+0x2f0`); then it spawns a `smoke_02` particle (`Media/Prt/smoke_`) and adds 1.0 to creature `+0x16a4` (use counter). Engines out of the 30-unit radius are untouched, hot or cold, so "cold parts rose to 100" means cold engines near a module.
* Trigger, manual (player): `FUN_140081520` (renamed `Creature_UseExtinguisher`): in the creature's module list `+0x1468..+0x1470` (0x18-byte records, pointer at `+8`) find the first module with charge `+0x800 != 0`, set it to 0 (consumed), then call `Part_ExtinguishNearbyEngines` on **every** module of the list (all modules cool their own surroundings at once). Called by tail jump from the key-release handler `FUN_14018a530` for the action code **0x1016** (4118; case of the jump table at `0x14018abd0`, entry at `0x14018a8cc`; guard byte `0x143a11909 == 0`). It is a release event of that action, so a held key does nothing until released.
* Trigger, AI: `FUN_1400812a0` (renamed `Creature_AiAutoExtinguish`, called from `AiShipTick` `0x140065676` and `aiShipDriver` `0x140073ba5`): counts engines with `+0x2f4 != 0` (and `FUN_1400457d0` flags); if more than 20 % are burning, or the burning fraction among class-flagged parts exceeds 20 %, and this has lasted 3.0 s of `GameClock` (timer `creature +0x1978`), it does the same consume-and-cool call. So an AI ship extinguishes after 3 s of widespread fire.
* So in 1792599418 the player (or the test script) released action 0x1016 at 23.72, 26.22 (2.5 s apart), 31.96 and 35.18; each time one extinguisher charge per module was used (a module has one charge until reloaded; with several modules, one is consumed per use). It does not occur in 1792612319 because that action was never released there. Condition for the sim: the action key (0x1016) release, a module with `+0x800 != 0` in the list, and the engine within 30 units of a module.

## 8. Fire (burn) law, `Body_BurnUpdate` `0x140054850` [V]  (added 2026-10-21, later)
Called at the end of every `Body_ThermalStep` with the same `dt_step = dt*4/n` (0.08 at 50 Hz). Stats fields: ignite temperature `Stats+0xbc` (engines 400), burn heat `Stats+0xc0` (engines 10; fuel tanks 200 per the existing plate comment). Part fields: flame value `+0x2f4` (non-zero = burning, 8 floats set together), per-part burn cap `+0x334` (float from the object property in `bodySecondaryInit` `0x140026a31`; parts with `+0x334 == 0` never burn), crew count `+0x804`.
* **Ignition**: not burning (`+0x2f4 == 0`) and `T >= Stats+0xbc` -> burning: `+0x2f4` := `Random_Float(0.5, 1.0)` (`1.0..1.5` when the part's double field `+0x7f8` is non-zero), "ON FIRE" popup (`displayTadsDamage_`) when the part has an owner creature and the logic id is not `0xd2`; for the player's ship also an alarm (`rep_1402a2f40_New(2)`). The part is appended to the burning list `DAT_1403c6700` (max 10000; used by `World_ThermalPass` for flame and smoke particles).
* **Each call while burning**: `Body_ApplyDamage(part, min(+0x334, 0.25 * dt_step), directFlag 0, ..., 0, 0)` = **at most 0.02 hp per tick (1 hp/s) per burning part**; direct flag 0 means the armour threshold (`Stats+0xc4`) is skipped; hp is clamped to `[0, +0x2cc]`; the player's ship takes x0.6 under the profile flags (`Profile+0x164/0x165`, as in `Body_ApplyDamage`). Then `T += dt_step * Stats+0xc0` (engines +0.8 per tick), so **a burning engine self-heats towards `T = 0.8 / 0.0016191 = 494` (before conduction and dose), just under the 500 overheat limit**. Burning fuel tanks (200) run away. If the part holds crew (`+0x804 != 0`) and `Random_Float(0,1) > 0.95` (5 % per tick), **one crew member dies per call** (`+0x804 -= 1`). A global burn counter `0x143a11924` is incremented per call.
* **End**: as soon as `T <= Stats+0xbc` (strictly `T < ignite` or equal) the flame values are zeroed (no hysteresis; `+0x334 <= 0` also ends it). The extinguisher action (T := 100) therefore ends all fires of the engines in its radius at the next tick.
* Check against the Kormoran telemetry (1792599418): `hp_sum` falls in bursts of about 3.6 per 40 ms = 0.02 hp x 90 burning parts per tick, and by 0.1 per 40 ms for a single burning part; the bursts follow the engine temperatures crossing 400.

## 9. Extinguisher charge (added 2026-10-21, later) [V]
* Module charge `+0x800` (float): initial value from the object property read in `bodySecondaryInit` (`0x140026acc`), and set again to **`Stats+0xf4` of the part's record** (0 if no stats) in the ship set-up routine at `0x14020ee0b` (inside the function at `0x14020eba0`, called by `0x14020ef30`), which loops over the creature's engine list (`+0x1330`); this runs at ship creation, not during a battle.
* Consumed only by `Creature_UseExtinguisher` / `Creature_AiAutoExtinguish` (set to 0 on the first module with a non-zero charge). **No in-battle reload writer exists** (every store to `+0x800` is listed above), so each module gives one use per battle.
* `Creature_AccumulatePartStats` (`0x140071380`) sums the remaining charges into creature `+0x16a8` and the maximum (`Stats+0xf4`) into `+0x16ac` (UI counters); `+0x16a4` counts uses.
