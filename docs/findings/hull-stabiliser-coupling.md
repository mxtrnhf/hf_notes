# The hull stabiliser torque and the bodies it is coupled to: what the game does, what the logs show (v1.163), ghidra-miner, 2026-10-21

Answers the simulator's "stabiliser share" questions. Data: `hf_ml/data/sim_runs24` (Intrepid, session 1792598385, Q hold t 120-137) and `sim_runs22` (stock Lightning, session 1792593593, t 93-109.5); hook rows E / X / T / S and b2 / torque-probe rows. Code: [hull-stabiliser-engine-logic.md](hull-stabiliser-engine-logic.md). Tags: **[V]** read in 1.163, **[log]** measured on the logs above.

## 1. The torque call, verified [V + log]
* Case 200 (`creatureLogic` `0x140035652..0x1400357d1`) re-read instruction by instruction: `frac = m_at / gate` (0 if `gate == 0`); `Tw = -w * I * kd * frac`, `Ta = -a * I * kp * frac`; idle bank (`+0x17fc == 0` or `+0x1800 == 0`): `Ta = 0` and `Tw *= 0.5`; `+0x15b4 == 0`: `Tw = 0`; `T = Ta + Tw`; **if `|T| > m_at` then `T = sign(T) * m_at`** (compare is on the absolute value against `m_at`, `m_at` = the part's own `Stats +0x100`, NOT scaled by `gate`, bank sums or the number of calls); then `Body_AddTorque(Frame, T)` unless `dt (0x1403c126c) == 0`. So the simulator's description (clamp `+-m_at` per call, `frac = m_at / gate`) is exactly right.
* `Body_AddTorque` (`0x140019be0`, vtable `+0x1a0`): `w_b2 += T * 0.05^5 * invI_b2` on the **Frame's b2 body only** (`this +0x178`, else the master's), immediately, no accumulator, no joints, no children. `invI_b2` is the Frame b2 body's own `+0x9c` = 1 / I about its **centre of mass**.
* **Measured: the Frame's spin jump between the exit of step n-1 and the entry of step n equals `sum(T) * 0.05^5 * invI_com` with ratio 1.000001 (Intrepid) and 1.000000 (Lightning) over 750 ticks each** (regression of `E(n).w - X(n-1).w` on the logged T rows). So nothing else in the game scales or redistributes the torque before the step; all of the per-design "share" effect happens inside `b2World_Step` or in the sim's own T.

## 2. Which inertia `I` goes into T [V + log]
`I = Body_GetInertiaAboutOrigin(Frame)` (`0x140048440`) = `(m * |localCenter|^2 + I_com) / 0.05^5` of the **Frame's own b2 body only** (children are separate b2 bodies and are not summed; there is no creature-level sum). It is the inertia about the body ORIGIN, i.e. larger than the `I_com` that `AddTorque` divides by. Per design (S rows of the player only, `part != '?'`; the `?` rows are the enemy ship):

| | Frame mass (b2) | `I_com` (b2) | `I` in T (b2) | `R = I / I_com` | `m |c|^2` | `|c|` (Frame origin to COM) | engines running case 200 | gate | clamped calls | idle bank | `|w|` median |
|---|---|---|---|---|---|---|---|---|---|---|---|
| Intrepid | 281.5 | 163.62 | 179.75 | **1.0985** | 16.1 | 4.8 game units | 4 swivel ENGINE_04 (m_at 1e7 each) | 4e7 | **49 %** | 40 % | 1.59 |
| stock Lightning | 167.0 | 70.85 | 91.33 | **1.2892** | 20.5 | 7.0 game units | 4 ENGINE_04 + 2 static ENGINE_05 (1.5e7 each) | 7e7 | **0 %** | 1.6 % | 3.02 |

* So the nominal spin change per call is `dw = -w * kd * frac * R` (unclamped), **R differs by 17 % between the two designs**. If the simulator takes `I` from the logged S rows it already has this; if it uses the Frame `I_com` (70.8 / 163.6) its T is 22 % (Lightning) and 9 % (Intrepid) too low.
* The clamp threshold is `|w| = gate / (kd * I)`: Intrepid 1.39 rad/s (x2 when the idle-bank halving is on), Lightning 4.8 rad/s (never reached in the window). So the two windows are in **different regimes**: Intrepid is clamp-bound half of the time (per tick the change is then `sum(m_at) * 0.05^5 * invI_com`, independent of `w`, `I`, `gate`), the stock Lightning is purely linear damping `0.05 * R * sum(frac)` per tick (`sum(frac) = 1` when both banks fire).

## 4. Box2D step [V]
`SomethingPhysicTask` calls `b2World_Step(world, dt, 10, 10)` (`R8D = R9D = 10` at `0x14028657e`): **10 velocity and 10 position iterations**; `dt = XMM6 / 50.0` with `XMM6` the frame time scale (`0x1403c0de4` = 50.0), i.e. 0.02 s at the normal rate; warm starting on, continuous on, sub-stepping off (world flags `0x1000101`, [box2d-physics-setup.md](box2d-physics-setup.md)). Joint softness: only what the K rows show (leg distance joints 10 Hz / 10, antenna welds), all set by the game per joint; the revolute joints are stock rigid pins plus motors.

## 5. What this does and does not explain
* The rigid-coupling expectation: if every child were rigidly joined and the solver converged within the step, a Frame-only spin jump `dw` ends as a common spin `dw * I_com / I_assembly`. Using the torque-probe masses and COMs (24 bodies at the first logged tick): Intrepid `I_assembly = 178.6` (extra 14.99, the assembly COM is only 0.5 game units from the Frame COM, so `M d^2 = 0.18` is negligible), ratio 0.916; Lightning `I_assembly = 89.06` (extra 18.2, `M d^2 = 0.03`), ratio 0.796. The simulator's fitted extras are 13.5 (Intrepid, ratio 0.924: 0.8 % from rigid) and 10.9 (stock Lightning, ratio 0.867: 9 % above rigid). So **the Intrepid is rigid-coupled within 1 %, and the stock Lightning responds ~9 % more strongly than rigid coupling predicts**; that deviation is what the 0.6 "share" absorbs.
* The assembly-COM hypothesis (inertia about the Frame COM vs about the assembly COM) is **refuted** (differences 0.03 to 0.18 b2 units).
* Candidate mechanisms for the Lightning excess that the data cannot separate yet [open]: (a) the motor reaction of the swivel-engine servos on the Frame during the Q hold (maximum motor torque 300.76 per engine times dt 0.02 = a 6.0 angular impulse, comparable to a whole tick of stabiliser impulse `0.02 rad/s * I`); the sim's servo gain and speed law decide it; (b) the two static ENGINE_05 calls (which exist only in the stock Lightning) and their thrust torque on the Frame (static engines are fixtures of the Frame, their force goes to the Frame); (c) incomplete joint convergence for the soft leg joints. The share tracks `sum(m_at)` only in the sense that the stock Lightning has statics and the unclamped regime; the code gives no place where `sum(m_at)` or the call count enters T besides `frac` and the clamp.
* **Decisive test (cheap in the sim)**: replay the logged sequence instead of the formula: for every tick feed the sim the logged `E(n).w`, the logged T rows (`who = F`, `ret = 0x357d1`) applied as `dw = T * 0.05^5 * invI_com` on the Frame, the logged force rows, step the assembly once with 10/10 iterations, and compare with the logged `X(n).w`. The per-tick residual `X_sim - X_log` (before any accumulation) isolates the children coupling from any error in the sim's T. Do it once on the Lightning (unclamped) and once on the Intrepid; if the Lightning residual is proportional to the logged T, the coupling model is wrong; if it is proportional to the swivel servo motion, it is the motor reaction.
