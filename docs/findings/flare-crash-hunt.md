# Flares and the proximity-fuse crash (1.163): fixed upstream; flare mechanics kept here

Status: **solved by highfleet-qol, `enable_flare_crash_fix` (1.163 only).** The crash site was not found by our static read; logdot's fix identifies it. Tags: legend in `../../README.md`. Read from the decompilation and from the qol source, not reproduced in game by us.
Why AI ships never use flares (a different question, solved): [ai-flares.md](ai-flares.md).

## The crash and the fix
Roadmap bug: "a proximity-fused missile colliding with flares crashes the game". The fix is [`src/flare_crash.rs`](https://github.com/logdot/highfleet-qol/blob/main/src/flare_crash.rs) (qol commit `f5423ca`, checked 2026-10-15; README: "Prevents the 1.163 missile-fuze crash when a flare's linked object is no longer available", default on, "not required on 1.151"; the source says it restores 1.151's nullable fuze-link check) [code].

* **Site [code]:** `0x140036bb5` (`MOV RBX,RAX; MOV RCX,RSI`, 6 bytes `48 8b d8 48 8b ce`) inside **`creatureLogic`** (`0x140033b90`..`0x140045128`; Ghidra's function lookup returns nothing for this exact address, but the body range contains it), right after `CALL 0x14021b070`. The patch inserts `TEST RAX,RAX`; non-zero replays the two instructions and resumes at `0x140036bbb`, zero jumps to the function's early exit `0x140036ca2` (the same exit that `0x140036b98` and `0x140036ba7` already use).
* **What is null [code]:** `0x14021b070` (Ghidra name `GetPropertyLinkedObject`) returns `p->+0x100->[0]->+0x10->+0xb8`, or 0 when `p` or `p->+0x108` is 0. The caller uses the result (`RBX+0x1840`) without testing it. qol's wording ("a flare's linked object is no longer available") implies a flare's link can be null when a proximity-fused missile reaches this code, and the unguarded result is then dereferenced [the fix mechanism is read from the qol code; only *why* the link is null for a flare was not checked]. 1.151 has the check, 1.163 dropped it (not compared by us in Ghidra; taken from the qol source).
* **Our earlier guess was close but off [guess, now checked]:** we expected a missing null check on a linked object and put the crash in `creatureLogic`; both held. The pointer was the property link (`0x14021b070`), not `GetStats` and not the owner link `+0x2e8`/`+0x480`.
* **Open:** not reproduced by us. Where exactly the missile's proximity test selects a flare, and whether other callers of `0x14021b070` in `creatureLogic` (`0x140043112`) need the same guard, was not read.

## Flare mechanics (kept: `ai-flares.md` and `systems.md` rely on these)
* **How a flare is released:** the player-input update `FUN_14007eb50` (called with `FireGuns`, `FUN_14002f480` and the "flare" sound string at `0x14007f904`) loops over the ship's launcher lists and calls **`FUN_14002eed0` (the flare release)** for the list at `+0x1408..+0x1410`
  when the flag `+0xbc0` is set (the flag at `+0xbbd` drives `FireGuns`, `+0xbbe` drives `FUN_14002e7d0`). `FUN_14002eed0` refuses unless the launcher has its cooldown at `+0x848` at zero, is armed (`+0x80c`, `+0x818` non-zero) and has count `>= 1` (`+0x860`, which is the ammo counter,
* **The flare body [code]:** `timeToLive` (`+0x2c0`) 5.0 s, **`logic` (`+0x3c4`) = `0x44c` (1100)**, layer/state (`+0x1f0`) 0, sprite id (`+0x8d8`) 5, drag (`+0x1dc`) `0x3a378034` (about 0.0007, the same as AP shells), velocity along the launcher direction x 400 with a random angle +-0.2 rad,
* **What `FUN_14002f480` is:** the close-in point-defence burst of the "strides" sprites (`strides`, `strides_fire`), not a flare function: it picks an incoming projectile within 60/120 units and angle < 45 degrees, subtracts 1 from the launcher's count (`+0x860`) and calls the target's `+0x200` (damage) with the target's
  own explosive power. It excludes targets whose stats `+0xb0` is `0x4000` (tactical missile) / `0x8000000` (strategic) / `0x200000` (bomb), and it **does null-check `GetStats`** before reading `+0xb0`. This confirms the earlier "KAZ burst" label.
* **The destroy handler `FUN_140023ac0`** (called from `FUN_14006aab0`) reads stats `+0x180` (`fuze_type`) 1 and 2 on a body being destroyed, again after `GetStats(...) != 0`. It is the "ammo explosion / bomb explosion / leg / engine lost" message and effect handler, not the proximity trigger.
