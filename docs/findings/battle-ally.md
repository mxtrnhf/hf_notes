# Battle ally: an AI-run, player-side ship that fights beside you

Status (2026-10-16): **`hf_ally` v0.8.1**: AI allies from the reserve (per-ship buttons on the pre-combat screen choose who may come, `max_allies` how many fight at once, a lost ally is replaced by the next ship switched on), retreat with or without them, F8 retreat order, a per-battle summary line. Several allies, replacement after a retreat order, and "unset = no ally" confirmed in play 2026-10-16 (v0.8.1); an ally destroyed in battle is not yet seen. Dated run reports are in [../runs/ally-runs.md](../runs/ally-runs.md) and [../runs/ally-probe-run-1.md](../runs/ally-probe-run-1.md). Tags: legend in `../../README.md`. Addresses are 1.163 (image base `0x140000000`) unless stated.
Goal: when a battle starts, bring a second ship onto the player's side. The player flies one ship; the other is run by the stock AI (it "copies the enemy AI" for now) and attacks the same enemies.

## Address warning (a mistake in an earlier summary)
Ghidra labels of the form `rep_<hex>_Name` carry the **1.151** address in the label, not the 1.163 one. Example: the 1.163 function at `0x1402672c0` is labelled `rep_1402454a0_New`; the correct 1.163 address is `0x1402672c0`. Always take call targets from the `CALL` operand in the disassembly, never from the label. (Same for `rep_140205f80_Creature__CalculateStats` = the function at `0x140223830`, `rep_14006fe20_shipKill_` = `0x1400739c0`, and so on.)

## What decides "AI-run" [code]
* **Add-to-level hook of a Creature: `FUN_14006bf60(creature, removing)`** (`0x14006bf60`; no direct callers; the only data reference that looks like a vtable slot is `0x140354cf0`, which table that belongs to is unverified. The other `0x148xxxxx` data reference seen on many functions is most likely an unwind-table entry, not a vtable). With `removing == 0` it:
  * always appends the creature to the **global creature list** `0x143faa5d8` (end pointer `loopVar10e0_`, 0x18-byte `Link` entries, pointer at +8);
  * appends it to the **AI vector** `0x143faa608` (end `0x143faa610`) **only if the byte `creature+0xbd4` is non-zero**;
  * puts the raw pointer into a **side bucket** chosen by the sign of the float `creature+0xad4`: negative -> vector `0x143faa5f0..0x143faa5f8`, zero -> `0x143faa650..0x143faa658`, positive -> `0x143faa638..0x143faa640` (skipped if state `+0xbdc == 6`).
* **`SomethingAITask`** (`0x1400111b0`) walks the AI vector, calls `vtbl+0x78` (is-active) and then the per-ship driver `0x1400739c0` for each entry. So a creature is AI-run when `+0xbd4 != 0` when it is added; side is not part of this test.
* **Per-ship driver `0x1400739c0`** switches on the state int `+0xbdc`: states 1 and 2 call the AI tick `FUN_140062f90` (after `FUN_140079b20(ship, 1)` when the float `+0xbc4 >= 0.5` and mode `+0xb48 != 1`); 0 and 7 call `FUN_14006cb30` (follow/hold, no shooting); 4 is a variant of the same. For states other than 4, 5 and 7 (and 6) the driver first re-derives the state: 0 if both target links (`+0xb00`, `+0xb18`) are empty, otherwise 1.
* **Target choice `FUN_140078b40`**: candidates come from the global creature list; a candidate is a foe when `side_self * side_other <= 0` (a **neutral side 0 counts as foe for everyone**), evac pods excluded, and it is ranked by distance (`-20` if it has no weapons). The choice is stored in the link `+0xaf8`/`+0xb00` and re-rolled about every 3.0 s (`+0xb28`). `FUN_140220170`/`FUN_140220120` are the same-side tests.
  * Consequence [code]: a ship with a **positive** side never targets the player's side and does target negative-side ships, and enemies pick it as a foe (product < 0). Nothing here needs the ally to be special.
* **Control** of the player's ship is separate: a smart-ref global `0x143a1c260` holds the controlled creature (written by `SetLink`). In the Missile scenario it is written only for the first spawned ship whose float `+0xad4 > 0` (`0x1402d4c4f`..`0x1402d4c77`: `CALL 0x1402a7e20(profile, ship)` then `SetLink(0x143a1c260, result)`).

## Spawn recipe seen in the Missile scenario [code]
`FUN_1402d45c0` (SCR_MISSILE state 1, called at `0x1402c4dfc`) is the only complete example read so far of "spawn up to four ships from a sorted list, one is controlled, the rest are not":
1. The defender fleet's ships are sorted; for `i < 4` it pops the next ship (a `Property` that links a ship **template** node), computes a position from the level bounds (`lvlHighXHighY`/`lvlLowXLowY`, staggered by `i`) and calls **`0x1402672c0(template, &pos, 0, 0)`** (call at `0x1402d4ba3`). That function copies the template's parts into a fresh Creature, runs `CalculateStats`, the sub-initialisers, resets ammo from the stats record, plays an optional radio sound and returns the Creature; the template node is killed through `vtbl+0x48` (the template is *consumed*, so the parts end up in the new ship).
2. Mode split on the flag held in `R13B` (derived at the top from a field of the A-list entry):
   * flag set: `FUN_140079b20(ship, 1)`, `+0xbc4 = 1.0`;
   * flag clear: `FUN_140079b20(ship, 3)`, `FUN_14022c010(ship, 1)`, `0x140223830(ship, 1, 0)` (recalculate stats), `+0xbc4 = 0.0`.
3. `+0xc98 = i`, the ship is appended to the roster vector `0x147fc7590` (`end 0x147fc7598`), and for `i == 0` the controlled link is set (above).
4. The state `+0xbdc == 7` is reset to 0 in teardown `FUN_1402d4f20`.
What is **not** yet found: where `+0xad4` (side) and `+0xbd4` (AI flag) are written for these ships. They may come from the template (saved ship data) or from `0x1402672c0`/its callees. The log-only prototype reads both on every add, which settles it.

## Teardown (the return path) [code, partly]
`FUN_1402d4f20` (end of the scenario state) walks the global creature list: for every creature with `+0x48 != 0` it resets state 7 to 0 and calls `MakeGlobal` (`0x1400609f0`) and `APP_MoveVolume` (`0x1401f3c10`), then positions fleets from the A-list and frees the roster vectors. It was read for the Missile scenario; **whether Combat's teardown returns every roster creature to its fleet is unverified**, and it is the most expensive way for this idea to fail (the second ship could be lost or left dangling). Test on a backup save.


## The vanilla reserve, wingman and redeploy machinery [code]
Found by following the SPAWN caller `0x2d6f7f`. This replaces the "build a template from nothing" plan.
* **Per-frame battle manager `FUN_1402cc260`** (called from `SomethingWithLevelSerias` at `0x1402c29f5`, prologue `48 8b c4 57 48 81 ec a0 00 00 00`). It owns three global vectors/lists: the **reserve list `0x147fc73b0`** (a `std::list` of ship templates: sentinel pointer at +0, size at +8), the **roster `0x147fc7590..0x147fc7598`** (0x18-byte `Link`s, ship pointer at +8) and a vector at `0x147fc73d8`.
* **Redeploy:** when no roster ship has `+0xd70 == 1` (a ship the player flies), a cooldown (`0x147fc7020`) expires, it calls **`rammingCheckCollision__` = the deploy function `0x1402d6e90`** (the Ghidra name is wrong). That pops the front of the reserve, spawns it through `0x1402672c0`, appends it to the roster and to the global creature list, makes it the controlled ship and returns `Profile.default > 0`. So the second ship of a fleet is a **reserve that deploys only after the first one is lost**, which is vanilla behaviour.
* **Deploy signature** `bool f(list*, roster*, u64* pos_out, u64 one, f32 x_lo, f32 x_hi, f32 y_lo, f32 -300.0, u32 aggr_bits=1.0f, i32 slot)` with the manager's own arguments `x_lo = [0x1403c2bc8]+100`, `x_hi = [0x1403c2bc0]-100`, `y_lo = [0x1403c2bcc]+100`, `-300.0` from `[0x14035b974]`, `1.0f` from `[0x1403524d8]`, slot 0 (call at `0x1402cc628`). The deploy body: `New(template,&pos,0,0)`; `ship+0x15fc = ship+0x15f8`; `ship+0xbc4 = aggr`; `FUN_1401bccb0(ship,0)` (activates the engine parts, sets mode `+0xb48 = 1`); `ship+0xce0 = 0`; roster append; **`ship+0xd70 = 1`**; **`SetControlled(profile, ship, slot)`**; `SetLink(0x143a1c260 + slot*0x18, ship)`; global creature list append.
* **`SetControlled` = `FUN_1402a7e30(profile, ship, slot)`** (slot 0..3): the ship previously held by `profile+0x48+slot*0x18` gets `+0xbd4 = 1` (AI on), the new one gets `+0xbd4 = 0` (AI off). So **`+0xbd4` is simply "not player-controlled"**, and four control slots exist (probably for local multiplayer). The controlled-ship links live in `0x143a1c260 + slot*0x18`.
* **`+0xd70 == 2` is the BOMBING role, not a wingman** (corrected 2026-10-16, see "Roles" below): `FUN_140078b40` (target choice) has a special branch for it (ships on the same side with role 2 vote for the target their group already attacks) and the manager removes role-2 ships that wander out of the arena while idle. That is the strike run seen in v0.2.x.

## Retreat: the retreat point, extraction, and why a promoted ship could not retreat [code + game]
* **How a battle ends** (end of the per-frame manager `FUN_1402cc260`): when the roster `0x147fc7590` is empty and the timer `0x147fc7020` is zero, the result `0x147fc7004` is set to **-1 if enemy ships (vector `0x147fc73d8`) remain, 2 if none do**; with a non-empty roster and no enemies left it is **1**. After the battle the screens distinguish "casualties died" from "casualties escaped" (`RETRY_CASUALTIES_DIED` / `_ESCAPED`, in `FUN_1401f3c10` territory) from each ship's own state. So a **retreat is simply every roster ship leaving the arena alive**.
* **The extraction function is `0x14020ef30(creature, flag)`** (Ghidra label `rep_1401f3c10_APP_MoveVolume`, a 1.151 address in the name; the 1.163 function is at `0x14020ef30`, called by the manager at `0x1402cc3b3`). For a ship that is alive it hands the ship back to the profile (`MakeGlobal(profile, 0, ship)` after refuelling it and detaching parts), for a dead one (state 6 or 7) it dismantles it. The manager calls it with `flag = 0` for idle **mode-2** ships near the arena edge (margin about 1.5 x the ship radius). Other callers: the scenario teardown `FUN_1402d4f20`, `FUN_1402cc7e0`, `FUN_1402cce70`, `FUN_1402cd1f0`, `FUN_1402cb6a0`, `ClickFunc` (a shipworks action).
* **Battle set-up** `FUN_1402ca2b0` (runs at battle start): clears the reserve list `0x147fc73b0` and the vector `0x147fc75a8`, sorts the sides' ships by a weight, groups the enemy ships in threes and spawns them as waves (`rep_140245ab0_New`) with a wave timer `0x147fc7020 = 30.0`. `FUN_1402ca070` (per frame): drops dead entries from the reserve list and, when the wave timer is zero, flags the next group to arrive when a reserve ship is within 1500 units of the controlled ship [guess on details]. The player's own extra ships also sit in the reserve list `0x147fc73b0`, which is why the ally deploy pops from it.
* **How retreat works** [code, game]: the game keeps one **retreat point** in `0x147fc7638` / `0x147fc763c` (two f32 at an arena edge, picked by `pickRetreatPoint` `0x1402c9bd0`). The manager starts every frame with `retreatPointCheck(controlled ship)` (`0x1402cbc60`): within 1.5 x the ship radius of the point it **zeroes the point** and extracts the ship with `0x14020ef30`. A zeroed point means no retreat, so **after the flagship used it, the promoted ally had nothing to fly to**: that was the "Retreat: UNAVAILABLE". (An earlier version of this note blamed the roster never emptying; that is not the cause. The roster matters only for ending the battle.)
* **What the promotion does** [code, game]: when no roster ship has `+0xd70 == 1` the manager counts down the wave timer `0x147fc7020`, deploys from the reserve when it is 0, and if the controlled ship is missing or dead sets `roster[0]` to mode 1 and links it. Our hook runs before this, so an order given when the flagship is gone arrives a frame late (v0.4.0 showed the ally promoted with mode 1 / state 2).
* **What `hf_ally` does** (v0.4.x, config `auto_retreat`, `flagship_leaves`, `retreat_key`): `"retreat"` extracts the ally the frame the flagship is gone (the squad leaves together, the battle ends as a retreat); `"handover"` lets the game promote the ally and writes the saved retreat point back so the new flagship can retreat; the retreat key (F8) sends an AI ally to the edge with mode 2 + state 2 (the strike-run state, the manager extracts it there) and is ignored on a ship the player flies. All three confirmed in play, see [../runs/ally-runs.md](../runs/ally-runs.md). **Sounds (v0.10+, config `ally_sounds`):** `mission_start_01..03` when an ally is deployed, `mission_danger_01` when F8 orders a retreat, `radio_stall_01` / `radio_lost_energy_01` when an ally is destroyed; mechanism and pitfalls in [../sound.md](../sound.md). **A destroyed ally is not flagged state 6/7: it leaves the roster with its state (`+0xbdc`) still 1** (v0.10.1 log), so "state 6/7" never detected a loss and every summary said `lost 0` up to v0.10.1; v0.10.2 counts a vanished ally as lost unless it was retreating/extracted or no enemy was left.
* Still open: whether an extracted ally counts as escaped or lost on the end screen; a third ship still in the reserve is deployed by the manager as the next flagship (vanilla).

## Roles: `+0xd70` is the beta ORDER (found 2026-10-16) [code]
`orderSelect1` (`0x1401e82f0`) builds a per-ship ORDER menu from a table: value **1 `unset`** (`order_unset`), value **2 `bombing`** (`order_bombing`), value **3 `support`** (`order_support`); the ship's current role is its `+0xd70`. The clicks (`ORDER_SELECT`, `ORDER_SELECT2` in `ClickFunc`, `0x140137f87` / `0x140137fe4`) write `ship +0xd70 = gui +0xc00` and rebuild the menu. So the field earlier called "mode" is the **role**: 1 = default/unset (the flown ship has it), 2 = bombing (the strike run we saw), 3 = support, and the enemies use 0 (no role). The strings `PRESELECT_BORDER_ROLES` and `ORDER_SELECT_TXT` tie it to the beta clip (a role icon per ship before the fight). **Support (3) has never been tried with `hf_ally`**; the byte search for a literal `cmp [..+0xd70], 3` found none, so it may be handled through a register compare or not at all: the cheap test is `ally_mode: 3` in `ally.json`. Note for the mod: the battle manager treats role 1 as "the ship the player flies" (it counts roster ships with `+0xd70 == 1` to decide on promotion and redeploy), so an AI ally must never get role 1. Where the ORDER menu is shown in 1.163 (it is referenced from `mainMap` `0x14014309c`) is not read.

## Targets and ammo: what the AI ignores (found 2026-10-16) [code + game]
* **Prize ships**: the ship loader `0x1401b08a0` (label `rep_1401a0a70_LoadSeriaFile`) compares the loaded ship's **name** with `Pollux` and `Kadesh Mk1` (both in `Ships/`) and sets the creature byte **`+0xc19 = 1`** (the property `m_prize`, registered in `showShipData?` `0x1400744b0`) and `+0xad0 = 0`; a Discord remark confirms the idea ("ships for sale are hardcoded, not their designs but their names"). Other writers of the byte: the creature copy `0x14005f529` and the spawn function `0x140209b00` (a byte argument, stored at `0x140209c42`), so other callers can pass it too. Readers: the battle setup `FUN_1402ca2b0` (sets a global flag `0x1403c2b6a` when a prize ship is among the enemies), the per-ship driver `0x1400739c0` (around `0x140073c10`) and a few more. **The target choice `FUN_140078b40` never reads it**: it takes every active creature with side product <= 0 (side `+0xad4`), so an ally shoots the prize ships the player is meant to capture. No hardcoded flag is needed in `OL.seria` or the ship files (checked: no `m_prize` in the game data; the ships named Kastor/Pollux/Kadesh differ only by name).
* **Fix idea (not built)**: a post-hook on `FUN_140078b40` for ships in our ally list: if the chosen target (pointer `+0xb00`, link `+0xaf8`) has `+0xc19 != 0` and another enemy exists, re-link the target (`SetLink` `0x140194de0`) to the nearest non-prize enemy. The hook shape: entry trampoline that calls a copy of the stolen bytes as a function, then our code (the same technique as the ClickFunc swallow trampoline needs the prologue bytes of the function to be position independent: not checked for `0x140078b40`).
* **Ammo**: the selector on the pre-combat screen sets the ammo of the player's own guns. The AI weapon controller `FUN_14007a8d0` re-sets each gun's ammo slot (gun `+0x850`) on **every** tick for guns of caliber index 15, 20, 25, 30: `_AP` only if the creature flags `+0xc7c` and `+0xc74` are set and the target is within 1000; the proximity variant under `+0xc7d` and `+0xc75` / `+0xc76`; otherwise the plain shell; never `_INC` or `_LG` ([ai-tick-patch-sites.md](ai-tick-patch-sites.md) section 3). An ally has those flags clear, so it always uses the plain shell whatever the player chose. Missile and aircraft defence shows the same (the player's observation). Which field the selector writes (where the chosen ammo lives) is not read yet.
* **Fix ideas (not built)**: (1) set the proximity flags on allies whose selector says proximity (cheap, native, gets only the two variants the AI knows); (2) post-hook the weapon controller and write the chosen ammo back into the gun slots (works for every ammo type, needs the selector's storage); (3) both belong to the rule layer of "Where to take the AI" (target filter, ammo policy, focus fire).

## Prize ships and trade convoys: what is flagged and what a modder told us (2026-10-16)
* **Message from another modder** (kept verbatim in [../data/mail-trade-convoy-2026-10-16.txt](../data/mail-trade-convoy-2026-10-16.txt); community text, [guess] until checked): trade convoys are made by `spawnTradeConvoy?` during world generation; each has exactly one trade ship (Pegasus 12.5%, Odissey 12.5%, Kastor 25%, Pollux 25%, Kadesh Mk1 25%) plus escorts (2, or 4 in hard mode) drawn from Intrepid, Scarab, Ballistic, Talos, Slogger, Lightning, Meteor Mk3/Mk2, Courageous (hard mode: Kormoran or Negev) under a fuel rule, not a combat-value rule. **The player does not have to kill the trade ship: when all other enemies are gone the surviving trade ships are captured.** The escorts get a "non-priority" byte (`+0xBB1`, said to zero their sort key for strategic missiles; not verified by us, a byte search for that displacement finds only an unrelated hit in `GetDialogResult?`).
* **Checked here [code]**: the five names are in the executable next to each other (`0x14036d820` Pegasus, `+8` Odissey, `+0x10` Kastor, `+0x18` Pollux) with a data reference in `spawnTradeConvoy?` (`0x140208762`, `0x14020879b`), so the list is right. The prize byte `creature +0xc19` that `hf_ally` found is set by name only for `Pollux` and `Kadesh Mk1` in the ship loader `0x1401b08a0`, and the spawn function `0x140209b00` can set it from an argument, so whichever way a ship got the flag, the **flag at battle time is the thing to test**, not a name list.
* **`hf_ally` v0.9.1 `spare_prizes`** (default on; v0.9.0 had a bug, see below): a wrapper around both call sites of the AI target choice (`0x140073b93`, `0x140073c73`, `mov rcx,rbx; call 0x140078b40`) runs right after the choice. For an AI-run friendly ship (side > 0, AI flag `+0xbd4` set) whose target (the node at `+0xb00`, climbed to its ship the way `traverseLinkedListCreature_` does) has `+0xc19 != 0`, it re-links the target (`SetLink` on the Link at `+0xaf8`) to the nearest active enemy without the flag, or to nothing when only prizes remain (the ally holds fire). The battle line now prints `prize enemies N` and each re-target logs `ALLY target: ... would attack the prize ship ...`. Not tested in play yet: it needs a fight against a convoy.
* **Ally flares and evasion**: the `ai_flares` module of our QoL fork (branch `ai-flares`, `src/ai_flares.rs`) decided "AI" with `side < 0`, so friendly AI ships never used it. New config `ai_flares.allies` (default `false`): when set, an AI-run ship on the player's side (side > 0 and `+0xbd4 != 0`) counts too; the ship the player flies never does. Built and deployed 2026-10-16 as `highfleet_qol_ai-flares-v6-allies.dll`, not run yet.
* **First run of v0.9.0 (log `Highfleet_2026-10-16_16-21-51.log`) and the bug it showed**: `ALLY target: c=0x248e3880 would attack the prize ship c=0x2a963380; now c=0x248d7b80` repeated dozens of times a second for one ally, and the battle line said `prize enemies 0` although a prize ship was present. Cause: the helper that finds the ship of a target node climbed the parent chain (`+0x88`) like the game's `traverseLinkedListCreature_`, which returns the root PART of a chain, not the ship; the prize flag was read on the wrong object, so (almost) every target "looked like a prize" and the ally was re-targeted every tick. v0.9.1 uses the owner pointer (`+0xb8`) for parts and the node itself for a creature (class code 47), and logs a re-target only when the (ship, target, replacement) triple changes. The count at the first battle tick misses ships that spawn later (waves), hence "at the first tick". Flares on allies were confirmed in the same run.
* **Where the AI's ammo flags come from (first read, [code])**: `FUN_140079810` (called at the end of the target choice) re-rolls `+0xc74`, `+0xc75`, `+0xc76` every 30 s from the current target's stats (random against squared values of the target's `+0x1604`, `+0x15bc / +0x15b8` and the direction table at `+0x1568`). So the AI's ammo is a random draw per target; the player's selector is not read. An override (the proximity flags for allies, or the chosen ammo written back into the gun slots) would run after this function: the end of the target choice is the natural place, next to the prize hook.

## How many enemy ships a battle has (read 2026-10-16) [code, not tested]
The battle set-up `FUN_1402ca2b0` sorts the enemy ships of the engagement by a weight (`+0xf8`) and copies them into the enemy battle list `0x147fc75a8` **while the list count `0x147fc75b0` is below 5**: `cmp qword [0x147fc75b0], 5` at **`0x1402caaa0`** (8 bytes `48 83 3d 08 cb cf 07 05`, the immediate is the byte at `0x1402caaa7`). So **a battle has at most 5 enemy ships**; a one-byte change (to 6 .. 127) is the whole "maximum number of enemies" setting, and a `max_enemy_ships` option of a QoL-style patch would just write that byte (guarded by checking the 8 bytes first). The same function then spawns the enemies in **groups of 3** (`diffArrayDivBy24(...) == 3` starts a wave, the last group may be smaller), puts the waves 2500 units apart starting at 3000, and sets the 30 s wave timer `0x147fc7020`. Other readers of the count (`aiShipDriver` `0x140073c19`, the weapon controller `0x14007a8d0`, `FUN_1402d9500`, `FUN_1402cf2a0`) were not read, and the pre-combat screen has room for few enemy cards, so a larger number may need layout checks. Not tried in game.

## Where to take the AI [plan, nothing built; the stock AI is "dumb as rocks" in play, which is the main blocker for a playable ally]
The player's reading (2026-10-16): the stock AI is so weak that the ally is not worth having; the game's developers probably switched this wingman idea off for that reason. Ally and enemy run the same code, so one improvement serves both sides. Stages, cheapest first; each is a config-gated, default-off rule so the vanilla behaviour stays reachable:
1. **Constants** (operand repoints, no new logic): stand-off distance (0.35 x reach), the close-range weapon cutoff, ammo choice, the 1% launch roll with the 2.0 s cooldown, the 0.025 rad aim tolerance. Sites and bytes: [ai-tick-patch-sites.md](ai-tick-patch-sites.md). Exposes them as JSON values. Cheap, but only moves the dials the original authors set.
2. **A rule layer of our own** on the steering-waypoint hook the QoL flares code already uses (`0x140064a8d`, in the AI tick `0x140062f90`) plus the fire/launch flags: kiting at a chosen range, focus fire on one target, missile discipline (launch only when aimed and in range, keep a reserve), terrain/ceiling avoidance (the "rams the ground" failure), and for the ally a leash that keeps it near the player and out of the way of your fire. Rules are plain code, testable by log, and can differ per side.
3. **Harness before tuning**: a way to start a fixed battle on demand and to run game time faster (neither exists yet). Without it every change costs a manual campaign fight. A first version can be the existing probe lines over several battles (speed, shots, launches, damage dealt/taken per second) scored by a script.
4. **Automatic tuning** of the stage-1/2 knobs against that scenario set (random or Bayesian search; no learning inside the game).
5. **A learned policy** (last): the command interface is small (a waypoint, engine strength and angle, a fire flag, launches, flares), so a small network could run inside the DLL, trained by imitation from logged human play or by reinforcement learning. RL needs millions of steps and the game has no headless/fast mode, so imitation from logs is the realistic route.
Also needed for the ally specifically: health readout and ship swap (checklist item 4), flares and missile dump for the ally (QoL "is AI" test is `side < 0`), bombs.

## Fleets, landing and the location scene
Ghidra 1.163, read 2026-10-17. Found while hunting a crash on engagement start; dated evidence and corrections in [../runs/ally-runs.md](../runs/ally-runs.md#crash-hunt-2026-10-17-tester-logs-ghidra-leads-diagnostics-build-first-debug-runs). Tags: [code] unless marked.
* **Globals:** `CURRENT_LOCATION = 0x143a11940`, `PLAYER_ESCADRA_ = 0x143a13eb0`. Escadra = a fleet on the strategic map; the profile keeps them in a vector at `profile+0x1f8..0x200`.
* **Fleet (escadra) fields:** `+0x100` ship list, `+0x108` ship count; `+0x128` **side marker** (positive = player's side, negative = enemy; getter `vtbl+0x178` = `0x1400f5270`, setter `vtbl+0x180` = `0x140110400`, which also copies it to the ships; it is not a strength); `+0x340` location the fleet is at; `+0x461` detachment flag (`DetachShips` sets 1; merge takes the minimum, so a detachment can become 0); `+0x368` set to `9000.0` by `DetachShips`, meaning unread (the location walker accepts a fleet only if it is the player's fleet or `+0x461 == 0 && +0x368 <= 0`); `+0x498` / `+0x4a0` cached fuel total / capacity (rebuilt by `0x140115580`); `+0x520` shop object; `+0x478` is **not fuel** (summed on merge, meaning unknown).
* **Ship (creature) fields** (not to be confused with the fleet's `+0x100/+0x108`): `+0x100` / `+0x108` is probably the parts chain [guess; only `ship+0x108 != 0` is tested by the walker]; the position of a ship is read through the chain `*(*(*(ship+0x100))+0x10)+0xb8`, then `owner+0xa84/0xa88` (corrected: the first reading called this chain unchecked; the walker checks each step); `+0xb6c` = `m_incity`, `+0xb6d` = `m_landing` (registered property names at `0x140355208` / `0x140355218`, registered in `showShipData?` at `0x140074b39` / `0x140074b97`); `+0xbd4` AI flag (1 for every player-side ship on the map: it only means "not the ship flown now" [game, debug run]); `+0xd70` order (see [Roles](#roles-0xd70-is-the-beta-order-found-2026-10-16-code); baseline 0, the flown ship gets 1 and keeps it [game, debug run]); `+0xbdc` driver state (see above); fuel per ship: current `+0x1638`, max `+0x1640` (doubles).
* **Location spawn `0x140265d80`** (label `rep_140243f90_MakeGlobal?`, a 1.151 address in the name): walks all escadras of the profile, keeps those with `vtbl+0x178() > 0` (a side test, see above) and `escadra+0x340 == CURRENT_LOCATION` and the player/detachment condition, collects each fleet's ships and spawns a Creature for each via `0x1402672c0` (label `rep_1402454a0_New`); the last spawned ship becomes the controlled one. Null checks at each step; it does not free the templates (same template twice = re-use). Callers: `0x269120` (label `tutorialFundsMusic(char)`; really the return-from-market/shipworks handler) and `0x211220` (leave shipworks / editor). Shipworks/market single-ship spawns: `0x140264f20`, `0x140265070`, `0x1402109d0`, called from ClickFunc.
* **Scene state machine** `SomethingWithLevelSerias` (`0x1402ac970`): state variable `0x147fc6fc4`, dispatch at `0x1402bc1d9`. **Case 1** (`0x1402be029`) calls the location walker, then goes to state 2 or 6. **Case 2** (`0x1402be084..0x1402be11f`) calls `FUN_1400f5b40(escadra)` at `0x1402be0c8` with **no null check** for the escadra at `*(vec[0]+8)` of the player-side vector, spawns that ship, sets state 3. `FUN_1400f5b40` returns the first ship of the fleet with `m_landing` set, so case 2 is most likely the **landing-in-a-city scene** [guess]; the scene sets `m_incity=1`, `m_landing=R15B` with state 5 on arrival (`0x1402be96f`, `0x1402c0ead`) and clears them at `0x1402c4453`. Pre-combat builders are called from `0x1402c3ab1`, `0x1402c404d`, `0x1402c470f`.
* **Side vectors:** `0x143a158e0/0x143a158e8` = Links to the **player-side** escadras, `0x143a159c0` = the enemy side. Refilled when the engagement trigger fires in `UpdateStrategicFleet` (`0x140111ff0`, `0x140113f00..0x140114948`); other writers `FUN_1400e6920`, LoadCity `0x140263588`, `FUN_14028db90`, `FUN_14028dda0`, `FUN_140224ec0`, `FUN_1400beea0`, `FUN_140211220`. Merge, `DetachShips` and escadra-remove do not update them. Seen in play [game]: after leaving a city the player-side vector holds one entry with a NULL fleet pointer, after loading a save it is empty.
* **Merge `FUN_1400f8eb0(target, source)`** (callers `0x1400ec840` via `UpdateStrategicFleet`, `0x1400eea70` garrison logic): moves ships (with their fuel), the shop object (`+0x520`, `0x1400f35a0`), flags. **`DetachShips` `0x1402017a0`** ("DETACHMENT") splits and rebalances fuel so the new fleet holds `f * capacity` (f = 1.0 or the MAPMODE_MISSION_FUEL slider), taking it from the player fleet (`0x140111cc0`) and adding exactly that (`0x1400ea980`): fuel is conserved up to rounding. Nothing in the code deletes an emptied fleet, yet in play merged-away fleets vanish from the profile list [game]; the remover is not found.
* **Fuel refill** (`UpdateStrategicFleet`, `0x1401151b8..0x1401152b3`): amount = min(missing, rate * time step, base stock `+0x274`), each ship capped by its own max, so a faster rate only fills faster [guess on units].
* **Tooling note:** `ClickFunc` (`0x14012f120`) is huge (62 KB); the standard decompile tools fail on it. Use a Ghidra script or xrefs: [click-func.md](click-func.md).

## Combat fuel (read 2026-10-17, Ghidra 1.163) [code, not yet tested in game]
* **Combat fuel is the ship's own tank: `ship+0x1638` (f64, current) and `+0x1640` (f64, capacity).** The battle burns it in `0x14007a220` (Ghidra `rep_140075c70_Get_Profile_`, `(ship, amount, flag)`): it takes the amount from the tank parts (`part+0x7f8`) and from `+0x1638`, adds the burned amount to `+0x17f8`, and for the player's ship (`FUN_140293920`) fires the stock radio calls `radio_fuel_50/30/20/10` (`PlayRadioSounds_` cases 0xe/0xd/0xc/0xb) when `current/capacity` crosses 0.5/0.3/0.2/0.1. The map-fleet fuel (`fleet+0x498/0x4a0`) is a cached sum of the same per-ship fields, rebuilt outside battle.
* The HUD `FUEL_TADS` blink (`tacticalCombat` `0x1402ffa07`) tests `fuel / float(ship+0x1994) < 2.0`; the AI driver (`0x140073a5e`) sets an emergency flag when `+0x1638 == 0`. Spawn (`0x1402672c0`, `0x140267699`) saves the fuel at battle start as a float at `+0xbd0`.
* **hf_ally v0.12.0** `ally_fuel_retreat_percent` (0 = off) orders an ally out (`order_retreat`, same as F8) when fuel is at or below that percent of `ally_fuel_basis` ("capacity" or "battle_start"); logs `ALLY fuel:` every 10 s and `ALLY fuel low:` when it fires.
