# Static engines (D-30S / RD-59S) and the hull torque: force path, and a hull drag term the sim may be missing (v1.163), ghidra-miner, 2026-10-21

Request from the simulator session: sim_runs14/16 show a hull angular-velocity oscillation with a jump once per revolution on a ship with 2 static D-30S, smooth on the same ship without them, and engine torque that does not show up as angular momentum. Tags: [code] read in the 1.163 decompile, [inference], [open].

## 1. How a static engine's force is applied each frame [code]
1. A command reaches the part through `Part_HandleCommand` 0x1400533f0. A handler runs only if the command code is in the part's spasm list (`part+0x370`). A static engine carries only 102 (`0x66`, bank 1) and/or 103 (`0x67`, bank 2), so `Engine_ServoUpdate` (codes 100 / 0x65, the swivel servo, 0x140053690) never runs for it. Parts with a swivel joint use the same `Engine_ApplyThrustForce` for the force.
2. `Engine_ApplyThrustForce` 0x140028360 (command: `+4` strength, `+0xc` count, `+0x10` angle, `+0x18` force sum out). Gate: part `+0x818` (power) != 0, `weaponAmmoExtraAmount == 0`, owner is a Creature.
   * `a` = world angle of the part = `Body_AddWorldAngle` (vtable `+0xe0`, 0x140055ab0) = sum of the parts' `+0x138` along the master chain: **static engine `+0x138` (local mount angle, set at creation) + Frame `+0x138`**. The Frame's `+0x138` is written each step by `Body_SyncFromB2` 0x140054bf0 from `b2Body +0x38` (sweep.a, **unwrapped**, not reduced to +-pi); a part without its own b2Body is never written by `Body_SyncFromB2`.
   * `c` = command angle (`cmd+0x10`), world frame.
   * `g = cos(c - a)` (computed as the dot product of `(sin c, -cos c)` and `(sin a, -cos a)`). **If `g <= 0` the engine applies nothing at all.**
   * `F = Stats+0xf8 (GetThrust) * cmd.strength * g`, then x1.2 if the creature perk list `+0x1a30` contains 2; if creature `+0xbc4 < 0.5` then x0.01 (and `+0xbc4 == 0` is first set to 0.001); a TWR factor only under editor/arcade/debug flags (`DAT_147fc6fd4`, `DAT_147fc6fc8`, `DAT_147fc6f82`, `IsInEditor`). Fuel burn for the player ship (`+0xbd4 == 0`): `Creature_BurnFuel`, `0.8` factor with perk 3; if the fuel returns 0 the force is skipped.
   * Force vector `F * (sin a, -cos a)`, point = the part's centre, passed to `Body_AddForceAtPoint` (vtable `+0x170`, 0x14001b2c0).
3. `Body_AddForceAtPoint`: target b2Body = the part's own (`+0x178`) else the master's (`+0x88`); for a static engine that is the Frame's. Point to world with `Body::get_world_pos` (vtable `+0xe8`, 0x140055af0): rotate by the part's cached matrix `+0x8fc..+0x908 = (cos,-sin,sin,cos)`, add the part position (`+0x128/+0x12c`), then the same for the master. The Frame's matrix is refreshed from sweep.a in `Body_SyncFromB2`. Then `p * 0.05`, force `* 0.05^4`, added to b2 `+0x4c/+0x50` and torque `(p - sweep.c) x F` to `+0x54` (sweep.c = centre of mass `+0x2c/+0x30`), only if the b2Body type is 2 (dynamic), which also wakes it. There is no call to `b2Body::ApplyForce`.
4. The accumulators are consumed by `b2Island_Solve` (`w = (w + h*invI*T) * (1 - h*0.05)` per step, stock constants) and cleared in `b2World_Step` (flag bit 2).

Per-step order (`SomethingPhysicTask` 0x140286380): all bodies `vtable+0x168` (`Body_PreStepUpdate`, section 3) -> save previous state -> `b2World_Step(1/coreFrameRate, 10)` -> all bodies `vtable+0x160` (`Body_SyncFromB2`).

## 2. Anything with period 2*pi in the world hull angle? [code]
* Player: `Player_SendThrustCommands` 0x1402a9300 reduces the Frame `+0x138` to +-pi, builds `h = (sin a, -cos a)`, bank vectors `v1 = m + h`, `v2 = m - h` (or swapped; `m` = move vector, 0 when only rotating), and the command angle with `vectorCalculateAngles_` 0x14000dda0 = `atan2(v.x, -v.y)`: **the angle jumps by 2*pi where the hull passes +-pi**, but every consumer takes `cos`/`sin` (or a `floor`-based wrap in `Engine_ServoUpdate`), so no jump results. For a pure rotation command, `c` is the hull angle (bank 1) or hull angle + pi (bank 2), so for a static engine `g = cos(mount angle)` or `cos(mount + pi)`: **independent of the world hull angle** (and exactly 0 or negative for a bank-2 engine facing the same way, which then applies nothing).
* No sin/cos table in this path. The only table is `Sqrt_Cache`, used for `|v|^2 < 10000`, resolution 0.1 in `|v|^2` (see section 3).
* Not a periodic-angle bug in the engine path as far as I can see.

## 3. A hull-angle-dependent torque that is not an engine term: Frame air drag [code]
`Body_PreStepUpdate` 0x14001d440 (vtable `+0x168`, runs for every live body BEFORE every `b2World_Step`). For the Frame (class `& 0x1f == 0x1f`):
```
v = (Frame+0x130, +0x134)            game units / s   (b2 velocity / 0.05, written by Body_SyncFromB2)
vhat = v / |v|                        |v| from Sqrt_Cache[(int)(|v|^2 * 10)] when |v|^2 < 10000, else sqrtf  (quantised)
n = (vhat.y, -vhat.x)                 unit vector perpendicular to v
th = Frame+0x138 (unwrapped sweep.a), W = Frame+0x218, H = Frame+0x21c
A = | H * (-sin th * n.x + cos th * n.y) | + | W * (cos th * n.x + sin th * n.y) |
F = - vhat * A * min(W, H) * |v|^2 * 1.29 * 0.5
applied with Body_AddForceAtPoint at the local point P = (Frame+0x210, +0x214)
```
Only a Frame gets this; other bodies get a simple `c * 1.29 * |v|^2 * 0.5` (`+0x1dc`) at the centre (no torque), a gravity-like `(0, -9.82 * mass * +0x1e4)` at the centre, and a wind-like `|d|^2` term toward `(+0x1ec, 0)` (`+0x1e8`) at the centre.
* The drag acts at P, an offset point, so it produces a **torque about the centre of mass that depends on the hull angle relative to the velocity direction** (period pi from the `abs`, and it flips with the sign of the arm / velocity). It is zero when `|v| = 0`.
* A ship whose engines are symmetric (the nostatic design: swivel engines, no net translation when only rotating) has almost no velocity, so almost no drag torque. **Two static engines produce a net force while the hull spins**, so the hull drifts, and the drag torque appears and depends on the hull angle: a candidate for the angle-dependent residual and for the "resistance at 180 degrees" the user feels. It does not by itself explain the flat -480 N*m in the nostatic ship. [inference]
* **Check in the sim:** is this drag (and the +0x1dc / +0x1e4 / +0x1e8 terms) in the sim? If not, add it, and compare the residual of sim_runs14/16 against `-(P_world - COM) x F_drag`.

## 4. Who else writes Frame angular velocity, angle, torque [code, partly]
* Torque / force: `Engine_ApplyThrustForce` (above), `Body_PreStepUpdate` (drag etc.), `Body_AddForceAtCenter` 0x14001b5d0 (vtable `+0x178`, zero torque), weapon recoil and explosions are not part of this note. Nothing applies an opposite torque after `Body_AddForceAtPoint`.
* Angular velocity: `Body_SetAngularVelocity` 0x140051760 callers: `Body_TearOffFromFrame`, `CreateFrameFragments`, debris spawners `FUN_140023ac0` and `FUN_14022ad00` (random +-pi on spawned fragments, read), `SomethingWithLevelSerias`, `creditsScreen?`, 0x140019d60 and 0x140222510 (not read). None is a per-frame hull term. `b2Island_Solve` writes `b2 +0x48` as the integrator.
* No spin limiter, gyro or "assist" for ships found; `maxRotation` in `b2Island_Solve` is stock (pi/2 per step, i.e. 78.5 rad/s at dt = 0.02).
* Angular damping 0.05 is stock Box2D (`w *= 1 - 0.05*dt`): a steady loss of `0.05 * w` rad/s^2, which with `tau / I` of about 0.36 rad/s^2 gives a plateau near 7 rad/s (the nostatic plateau 7.15 is consistent with that; [inference]).

## Addendum 2026-10-21 (later): what changes b2 velocities between steps, and the unread callers [code]
* **`Body_SyncFromB2` 0x140054bf0 does not write into the b2 body.** It only reads `b2 +0xc/+0x10` (xf.p), `+0x38` (sweep.a), `+0x40/+0x44` (v), `+0x48` (w) and stores them in float32 game fields (`+0x128/+0x12c = p / 0.05`, `+0x138 = a`, rotation matrix `+0x8fc.. = (cos,-sin,sin,cos)`, `+0x130/+0x134 = v / 0.05`, `+0x13c = w` unchanged), clears the game force sums `+0x15c/+0x160/+0x164`, and computes `+0x140/+0x144 = dv / time_related_global_`. No blending, no write-back, no truncation beyond float32. `SomethingPhysicTask` before the step only copies the game fields into `+0x148..+0x158`. Both `Body_PreStepUpdate` (vtable `+0x168`) and `Body_SyncFromB2` (`+0x160`) are the base-class slots; 19 vtables reference them, and I did not check whether the Frame's vtable overrides either. ## Addendum 2026-10-21 (sim_runs17): a loss linear in the hull's spin; what I could and could not find [code]
Data: tau/w = 103, 111, 102 N*m per rad/s for close statics, wide statics and nostatic, i.e. about 1.45/s on I = 70.85, against Box2D angularDamping 0.05.
* **No term linear in angular velocity exists in the per-step forces.** `Body_PreStepUpdate` (0x14001d440) has: Frame quadratic drag at (+0x210,+0x214) [section 3]; for non-Frame bodies a quadratic drag `c * 1.29 * |v|^2 * 0.5` along `-vhat` with `c = Body+0x1dc` (`m_drag_lin`, default 0, nonzero only for shells/particles), applied through `Body_AddForceAtCenter` (no torque by itself); a constant `(0, -9.82 * mass * +0x1e4)`; and a wind-like term `+0x1e8 * |d|^2` toward `(+0x1ec, 0)`. `|v|` there is the body's own game velocity (`+0x130/+0x134`), which `Body_SyncFromB2` only refreshes for bodies that have their own b2 body, so a fixture-only part (static engine, gun on the Frame) has a stale or zero velocity and no drag. Nothing uses `Body+0x1e0` (`m_drag_ang`, default 1.0) in the physics path that I found (its readers are serialisation, a debug draw, FX).
* **b2 damping is only written at creation**: `Body_CreateB2Body` 0x14004b330 and `Body::Reflect` 0x14004b010 (the second creator of b2 bodies: it builds a free body only when the master is the global node, or a fixture on the Frame when the master is a Frame) both set linear and angular damping to 0.05 (def `+0x1c/+0x20 = 0x3d4ccccd`), gravityScale 1.0. A search for float stores to `[reg+0xa4]` found no b2-body writer (36 hits, all other objects). Immediate (integer-constant) stores were not searched. No body-type, sleep or fixedRotation toggle seen for ships (`b2Body` flag bit 0x10 is set only by the def).
* **Frame w readers**: the only per-frame consumer of the Frame's `+0x13c` I could attribute is `Body_SyncFromB2` (writer) and the AI (reads the hull angle `+0x138` and inertia, not w). Several unattributed reads of `+0x13c` sit in regions with no function (0x1400371e7, 0x14003927f, next to `creatureLogic`) and a write at `creatureLogic` 0x14003ad3f; not read.
* **Static-engine count or position**: `+0x166c/+0x1670/+0x1674/+0x1678/+0x167c/+0x1680` are read only by `CalculateStats` (0x1400804f6.., turning them into the display values `+0x1604..+0x1610` and the rating `+0x15f8`) and by UI code. No torque balance or asymmetry compensation exists; nothing in the force path uses them.
* **Sectors rule**: `Stats +0x128` (`m_mdl_sectors_type`) is used only in the sensor merge code (`Creature_MergeSectorArray`); `Part_HandleCommand` and `Engine_ApplyThrustForce` do not read it, and the thrust force has no velocity dependence (only `cos(c - a)`, the power gates and the 0.01 factor when creature `+0xbc4 < 0.5`).
* **Conclusion**: I found no code that explains a 1.45/s linear loss in the engine, drag, damping or Frame-velocity paths. Because all three designs show the same coefficient, it is a hull-level (or world-level) effect. Open suspects, in order: (1) **contacts** on the hull's b2 body (ground or boundary, friction; `b2ContactManager_Collide`, `ShouldCollide` 0x1402858c0) or contact with the ship's own jointed parts; (2) **jointed child bodies** (landing legs and turrets are revolute joints with motors, `Joint_SetMotor`, command 400 handler in `Part_HandleCommand`; a motor holding speed 0 resists relative rotation) that the sim does not model; (3) a damping value other than 0.05 on the live Frame body: confirm from the logger with a direct read of `b2Body+0xa4` of the Frame in the flight that shows the loss (the sim.27 G rows reported 0.05, so (3) is unlikely).

Ghidra change this round: created a function at 0x140078300 named `Creature_DebugDrawOverlay` (it was an undefined function; it only draws debug lines when `Body+0x...` debug flag is set, gated on the AI flag `+0xbd4`). Needs the user's check-in.

## Addendum 2026-10-21 (later): a design-dependent thrust reduction in `Engine_ApplyThrustForce` (editor / arcade / debug) [code]
Found while answering "does the hull receive less torque than the summed engine torque?" (sim.27, statics-wide flight 1792572919: no contacts, joint reactions ~0, Frame damping 0.05).
* In `Engine_ApplyThrustForce` 0x140028360, after the cosine gate and the x1.2 / x0.01 modifiers, the applied force `F` is multiplied by a factor `f(X)` **if any of these is true**: `DAT_147fc6fd4`, `DAT_147fc6fc8`, `DAT_147fc6f82`, `IsInEditor` (byte at 0x1403ef368, written by `loadShipworks?` 0x1400d25bc and `FUN_1400beea0` 0x1400c0173, i.e. **true in a Shipworks test flight**), or `FUN_1402213e0` (= `DAT_147fc6fe0 && ZOOM_LEVEL > 3`). Disassembly 0x1400285aa..0x14002860f.
* `X` = creature `+0x1608` = `(+0x166c + +0x1670) / (mass +0x15b8 * 9.82)` (0 if either bank sum is <= 0), where `+0x166c/+0x1670` are the bank thrust sums of engines that **swivel (have a 100/101 command) or whose part angle field is < 0.01** (`Creature_AccumulatePartStats`, section 5). So **X depends on which engines count: a static engine counts only if it is mounted straight**, and the factor changes between designs with and without statics.
* Formula (constants read: 6.0 at 0x1403547f4, 3.0 at 0x140352804):
```
f(X) = min( 1 , min( 3 , X/6 + 1 ) / X )        f = 1 when X = 0 (division gives +inf, clamped to 1)
F_applied = F * f(X)                              F = Stats+0xf8 * strength * cos(c-a) [* 1.2 perk] [* 0.01 if +0xbc4 < 0.5]
```
  Values: X = 1.2 -> 1.00, 2 -> 0.67, 3 -> 0.50, 4 -> 0.42, 6 -> 0.33, 9 -> 0.28, 12 -> 0.25, 24 -> 0.125.
* The factor scales the applied force and the thrust sums (`cmd+0x18`, creature `+0x17fc..`, bank sums) but **not** the flame effect or the fuel burn (`fVar20`, `fVar21` are only rescaled in the `+0xbc4 < 0.5` case). A logger that recomputes the force as `Stats+0xf8 * strength * cos` without `f(X)`, or a sim without it, over-estimates thrust and torque by `1/f(X)`.
* Whether a flight is affected: true in Shipworks test flights (ship name `TestProject`, see the campaign-vs-test note); false in a normal campaign battle unless one of the other flags is set. **The same ship can therefore fly differently in the editor and in the campaign.**
* This does not by itself make a loss proportional to spin. It scales all engine force and torque by one design-dependent factor, so test it against the sim.27 numbers: with `X` computed from the logged `+0x166c/+0x1670/+0x15b8`, compare `f(X)` with the observed delivered fraction (about 0.45 in the third fit).

### Force point and body for a swivel engine (answer to the lever question) [code]
`Body_AddForceAtPoint` 0x14001b2c0 targets the part's own b2 body if it has one (`+0x178`), else the master's. The torque is taken about **that target body's own sweep.c** (`+0x2c/+0x30`), and the point is converted by `get_world_pos` with the part's own matrix `+0x8fc` and position `+0x128`, then up the master chain. A part with its own b2 body has `GlobalNode_` as master (`Body::Reflect` creates the body only in that case), so the chain stops and the point is the part's `m_center` in world coordinates; there is no second transform. For a static engine the target is the Frame, with the Frame's matrix and sweep.c. I found no case where the force goes to a different body than the one whose COM is used for the lever.

## Addendum 2026-10-21 (coast test): is there a gyro / stabiliser that scales the Frame's spin? The unattributed `creatureLogic` sites [code]
Data (simulator, sim.27 session 1792572919, statics-wide, TestProject): after all keys are released the hull's spin falls 1.60 -> 0.656 rad/s in 0.6 s with zero engine force, no contacts and ~0 joint impulses, then the fall stops abruptly; the whole-system angular momentum drops 59%. nostatic: 7.15 -> 3.3 in 0.5 s.
* **The three sites are not a stabiliser.** They are in the per-part logic switch of `creatureLogic` 0x140033b90 (the switch on the part's logic id `+0x3c4`, with `RSI` = the part body being processed):
  * `0x14003ad3f`: not a write to a body's angular velocity. `RBP+0x138/+0x13c` is a **stack buffer**: it stores `(0, 3.0 * mass_of_linked_creature)` (`[RCX+0x15b8]`, constant 3.0 at 0x140352804) and then calls `Body_AddForceAtCenter` (vtable `+0x178`) on `RSI`. It is a constant lifting force for one logic id (a part linked to another creature, via `RSI+0x498`), selected by the case `[RBX+0x198] == 2`.
  * `0x1400371e7` and `0x14003927f`: both read the part's own `w` (`+0x13c`) and angle (`+0x138`) in a rocket / missile guidance case (they also set `+0x2dc = 3.0`, call `FUN_140029b60`, and use `Body_GetInertiaAboutOrigin`). Form: `torque = I * ( (target_angle - angle) * k_p * gain  - w * k_d * gain )`, clamped, then **`vtable +0x1a0` (AddTorque) on `RSI`**. A guided rocket's own PD controller.
* **vtable `+0x1a0` is `AddTorque` (0x140019be0, undefined function; referenced by 18 vtables, no direct callers).** Like `Body_AddForceAtCenter` it targets the part's own b2 body, else its master's b2 body. Its **seven indirect call sites**: `0x14000a308` (in `0x140009db0`, called by `AircraftLogic_Tick` 0x14000f7a0 and `0x140007de0`: aircraft attitude PD with a `-w` term), `0x140037286`, `0x1400392bd`, `0x1400392d9` (creatureLogic, the rocket PD above), `0x140060a49` (`FUN_140060a20`, a Creature override of the slot that forwards the torque to the creature's root Frame; referenced from vtable data 0x140354de0 and 0x14807a940, no code caller found), `0x1402be214` and `0x1402c07ed` (inside the level-script dispatcher region near `SomethingWithLevelSerias`, not read).
* **Other writers of b2 `w` or torque**: `Body_SetAngularVelocity` 0x140051760 (callers listed in the earlier addendum: none is per-frame hull control) and `b2Island_Solve`. I found no direct store into b2 `+0x48` / `+0x54` outside the solver, `Body_AddForceAtPoint`, `Body_AddForceAtCenter` and `AddTorque`; function-pointer or vtable calls to these were enumerated through the instruction search above, but a store reached only through inline code in an unattributed region could be missed.
* **No trigger on key release found.** `Player_SendThrustCommands` returns early when no key is held (after sending cmd 100 / 0x65 with angle 0 to the swivel servos, which only drives their joint motors). No timer of 0.5-0.6 s is visible in the engine / player path. Candidates still unexplained: (1) the creature `+0xbc4` value (thrust x0.01 below 0.5, x0.001 when it is 0), which looks like a ramp that could change after release; (2) b2 sleeping (`timeToSleep 0.5`, a sleeping island has its velocities zeroed), though a continued normal decay afterwards argues against it; (3) the AI attitude-hold (`AiShip_SteerController`) running on the player's ship (never confirmed; see [player-attitude-stabiliser.md](player-attitude-stabiliser.md)): it would apply bank-vector torque of `error * I / 20`, and its gate `+0x180c / I > 0.02`.
* **Decisive experiment**: hook `AddTorque` 0x140019be0, `Body_AddForceAtCenter` 0x14001b5d0, `Body_AddForceAtPoint` 0x14001b2c0 and `Body_SetAngularVelocity` 0x140051760 in the logger and log, for every call whose target b2 body is the Frame, the return address, the torque / force and the step number, during the key-release window (96.88 to 97.5 s). ## Addendum 2026-10-21 (AddTorque defined): `Body_AddTorque` writes the angular velocity directly [code]
`Body_AddTorque` 0x140019be0 (Body vtable `+0x1a0`; defined and named in Ghidra on 2026-10-21): `torque *= 0.05^5`; if the target b2 body is dynamic it is woken and **`b2 +0x48 (w) += torque * invI (+0x9c)` immediately**, not through the torque accumulator `+0x54`. So any caller changes the angular velocity at the call, bypassing `b2Island_Solve`'s force integration. This corrects the earlier list of "writers of b2 `w`": they are `b2Island_Solve`, `Body_SetAngularVelocity` and **`Body_AddTorque`** (callers in the coast-test addendum). For the sim.28 logger: hook `Body_AddTorque` first; a sink that acts on the hull's spin without any force or torque accumulator showing it would be visible there.
