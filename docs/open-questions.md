* **Salvos on the map:** AI fleets defending against our salvo: same `Missile.seria` setup, so the merge applies to them too? Map-level AA against a group (the three-crafts-per-pass rule, `FUN_140111110`)
  has not been read for bigger groups. A volley as ONE map object with count N (it would also fly as a group) is possible in principle; the `MapCraft` scenario `SCR_BOMBERS` is unread.
* **Multi-charge x salvo:** deliberately undecided. One A-101 part is one launcher switch (one queued launch at a time); several A-101 parts queue as separate launches and the merge treats them like any missile.
  Decide the intended use before testing or documenting it.

* Refuel: the buy-fuel slider and `REFUEL_TIME` are untraced. GOG 1.163 may share addresses with Steam 1.163; untested.

## Ghidra: fixes and questions to raise with logdot (no program has been edited)
Resolved items are gone from this list; see [version-differences.md](version-differences.md) for the evidence.
1. Ghidra's 1.163 `Body` struct is 0xa08 bytes and is the 1.151 layout; the object is 0xa40. `Escadra` is 0x600 (real 0x618), `Creature` 6358 (real 0x1a50), `Profile` is the stale 1.151 layout (vectors moved +0x48; endgame flags +0x58). `ShipPart` (stats record, 0x188 in 1.163) and `HGEVFTABLE` exist only in the 1.151 program.
2. `.conflict` duplicate types in the 1.163 program (`Body.conflict`, `BodyVFTABLE.conflict`, `DLL<Body>.conflict`, ...): delete after checking references.
3. The four air-group functions (`CreateMapAircraftGroup` = `0x14010f8e0`, `UpdateMapAircraftGroup` = `0x140117840`, `ComputeMapAircraftWeaponStrength` = `loadAircraftWeaponsFromBotMenu` (1.151 `0x1400e69a0`), `ConfigureStrategicMissileForTacticalBattle` (1.151 `0x140241680`; 1.163 address not found, search for the strings and masks it uses, not by similarity) have no 1.163 match from the fuzzy tool. **No function is defined at `0x140117840`**, nor in the `SCR_MAP` handler region `0x1402b8a00`-`0x1402b8b30`, nor for `FUN_140261a20` (the endgame function): create them after the review. `find_code_gaps` lists 7,316 gaps, most of them unwind fragments.
4. Wrong or misleading names: `mapCrafts` at `Profile +0x228` (really the Missile vector); the 1.163 comment "Ground defense creatures?" on `FUN_1400e4530` (builds the MapCraft); `0x1400739c0` labelled `shipKill?` (the per-ship AI tick caller); `0x140071120` labelled `...::sqrtf` (computes the ship bounding radius); `0x14007ffaa` sits inside `CalculateStats`; the 1.151 AI weapon controller `0x140076300` is named `...::atan2f` (its 1.163 twin `FUN_14007a8d0` is unnamed); `creatureLogic` is the projectile/missile/aircraft behaviour dispatcher, not the ship AI; the creature flags `damageCounter_` (1.151) / `linkDLL` (1.163) at the 700-range cap; 1.151 `mdl_covered` / `mdl_turbine` are swapped relative to what `UpdateEngineCovered` writes; 1.151 `fFireCharge`, `fFireRateTimer`, `fFireDelay`, `bFireStatus` do not match `FireGun`'s use of the fields.
5. `structures.md` entries now believed right but worth a second pair of eyes: `+0xd4` crew capacity (int) and `+0xc8` fuel capacity (double); `+0x858` reserve vs `+0x860` loaded rounds; `+0x270` of the Profile is the MapCraft vector.
6. Latent bug in both versions: the AI weapon controller looks up `ITEM_AMMO_230MM*` for caliber index 30, but the table has `ITEM_AMMO_203MM`. Harmless in vanilla (no part has `m_weapon_caliber=30`); it would bite a mod that adds a 203 mm gun. Is it intentional?
7. The `GetStats` getters of 1.151 (`GetLaunchedRange`, `GetMissileAp`, ...) name the stats-record fields; the 1.163 equivalents are `FUN_` and could take the same names.
8. highfleet-rs (`eb7bf42`): (a) projectile logic ids disagree between sources: ours 100/130/132/135/140/160, his adds **150** (AP airburst), `ammo-extended` lists 90 bounce / 180 directional proximity; no consumer of 150, 90 or 180 found: [findings/ammo-1151-vs-1163.md](findings/ammo-1151-vs-1163.md). (b) His 1.151 `ammo.rs` doc lists logic 132 and 135, which our diff says exist only in 1.163 (the 1.151 300mm rocket is 130); ask whether the comment was copied from the 1.163 file. (c) His `caliber` / `logic` field names are the reverse of ours; agree on one. (d) `fire_delay`: "aircraft only" versus the 1.151 name `gun_rate_time` with its "required for guns to fire" comment. (e) `TLL` as a `std::map` node: [structures.md](structures.md).
9. QoL build break (found 2026-10-14): `highfleet-qol` depends on `highfleet-rs` by git URL with no pinned revision and `Cargo.lock` is gitignored, so a fresh build or CI run resolves the newest `highfleet-rs`. Commit `cfa6ae28` (2026-10-13, 'Rename and document 1.163 ammo fields') removed `Ammo::unknown_180h`, which `src/plane_guns.rs:271` (`ammo_max_load`) still uses, so `cargo check --features 1_163` fails. Pinning `highfleet` to `3f6b54b3` in a local lockfile builds. Fix upstream: rename the field use, or commit `Cargo.lock`. Not fixed in our refuel/speed PR.
10. The modloader README still says the release zip is `Artifacts.zip` and yields both `bass.dll` and `bass.dll_`; v4.1.0's `Modloader.zip` has only the loader `bass.dll`, so users must rename the original themselves (see [install.md](install.md)).
11. Misleading Ghidra names found while tracing text drawing (2026-10-14; nothing renamed): `0x1401ae090` `displayOnUI?` = localised string lookup; `0x14016f290` `rep_1401637a0_...vsprintf` = `hgeFont::printf`; `0x14016eb40` `displayLableRotation?` = `hgeFont::Render`; `0x14016f120` `setfield_0x1020SideEffects?` = `hgeFont::SetColor`; `0x14016f0c0` `FUN_14016f0c0` = `hgeFont::SetBlendMode`; `0x1401703e0` `LoadNameIntoMedia` = `hgeResourceManager::GetFont`; `0x1401a8710` `rep_140198e70_LoadNameIntoMedia` = get-font-and-style helper; `0x140300c20` `rep_1402d5b50_WriteToClientLog` = scene dispatcher; `0x14030e670` (`cosf`), `0x14030a6b0` (`New`), `0x1403050a0`, `0x14030f250`, `0x140300db0` (`pow`) = per-mode render functions; `0x1400d4380` `rep_1400cf430_...memmove` = shipworks label pass. See [findings/render-pipeline.md](findings/render-pipeline.md).
12. The Ghidra `GUI` struct (3640 bytes) is the 1.151 `Body` layout reused as a placeholder; do not trust it. Real classes seen: `GUI::GUI_2` `0x14012a910` (0xe70), `Panel::Constructor` `0x14012b230`, `ObjectList::ObjectList` `0x14012b0d0`, `List` ctor `0x14012b000`, `GUI::Load` `0x140163110`, `GUI::Relink` `0x140165f70`, `GUI::HandleClick` `0x14012d050`. The input question (which code reads keys; `+0x290`/`+0x2a0` slot mapping) is still unresolved.
13. Native text drawing, still open (see [findings/render-pipeline.md](findings/render-pipeline.md)): other aspect ratios and resolutions (VideoTask letterboxes when screen and frame sizes differ; text should follow the frame target but is unproven; only 16:9 at 2560x1440 was seen); whether every editor state (part held, test drive, dialogs, save/load screen) runs the label-pass block; whether a font restyle and restore disturbs the game's own labels (screenshots looked normal); behaviour when the editor is entered from the main menu versus the hangar; whether the composite description of `0x140083450` is right.
14. Fonts (see [findings/fonts.md](findings/fonts.md)): what draws the Cyrillic stats panel text, since every `.fnt` is ASCII only; what the undeclared `flash_large_shadow_special.fnt` is for; which fonts the HUD, battle and map screens use; how fonts get their atlas rectangles (`Fnt1.res`/`Fnt2.res` not read); `fHeight` semantics at `font+0x1008`; whether `Render` clips; the look of the 38 fonts not yet sampled on screen and of the `*_blured`/`*_shadow` variants.
