# Mod-function port audit: hf_ally / hf_ai addresses in 1.151 (2026-11-11, round 4)

Goal: take every function and hook/scan address the `hf_ally` and `hf_ai` mods
hard-code against Steam 1.163, find where each lands in the 1.151 program,
and rename the 1.151 side where it was still unnamed or wrongly named.

Machine-readable result: `data/modaddr_163_151.tsv` (addr163, name163, addr151,
name151, status, evidence, mod_ref).

## Method

1. Extracted every `const ...: usize = 0x...` address and every documented
   address from `hf_ally/src` and `hf_ai/src` (42 code sites, 40 unique
   containing functions after resolving hook sites to their function).
2. Looked up each address's containing 1.163 function in the round-1 program
   inventory and checked the existing match tables (rounds 1-3) for a pair.
3. For the 34 functions without a chain: generated 1.151 candidates by
   interpolated spatial delta (+/-0x40000..0x60000) and instruction-count bands
   (1351 unique candidates), dumped per-instruction **mnemonic sequences** for
   all targets and all candidates with `DumpMn163/DumpMn151.java`
   (output `mn163.tsv`, `mn151.tsv` in /tmp work dir; addresses list:
   `cand151_addrs.txt`).
4. Ranked candidates by shared 8-gram mnemonic fingerprints, then confirmed
   the top hits with full longest-common-subsequence over the mnemonic
   sequence (not decompiler text - robust to register/temp renaming) plus
   mapped-callee set identity and string-set overlap. `!ClickFunc` and the
   other 5000+-instruction giants were only touched through listing
   scripts, never the MCP decompiler.
5. Decompiled cross-checks for the two functions whose current 1.151 names
   were to be replaced (both under 700 instructions, safe to decompile).

## No 1.151 twin exists

- `buildSquadPrecombatScreen` (0x1402d73a0) and its `secondaryPrecombatButtons`
  dispatcher seams: `TarkhanGUIDispatchOperator` has exactly one precombat-screen
  caller in 1.151 (mainPrecombatScreen), but two in 1.163. The standalone squad
  precombat screen is a 1.163 feature. Mod ports touching PRECOMBAT_B1/B2
  cannot be ported 1:1.

## Hook/scan sites

Sites inside functions do not map byte-for-byte between builds (register
allocation and inserted features shift them). The containing function maps
cleanly - see the site-holder rows at the end of
`data/modaddr_163_151.tsv` (all `hf_ai` STEER/BOOST/ARM/ROLL/LAUNCH sites live
inside AiShipTick -> TacticalAI_MasterUpdate; the flare hook and CREATURE
update sites inside CreatureUpdate -> UpdatePlayerTactical; the dead-node
detours inside CollectDeadNodes). Porting the mods themselves to 1.151 needs a
byte-pattern search per site (same technique the mods already use for prologue
validation), not address translation.

## Data globals NOT ported (follow-up)

The mods also hard-code ~45 data globals (LEVEL_NAME 0x1403c1390, RESERVE
0x147fc73b0, CREATURES_BEGIN 0x143faa5d8, CLOCK/GAME_TIME 0x143a119c0,
CONTROLLED_LINKS 0x143a1c260, BODIES 0x143a33c90, arena bounds 0x1403c2bc0,
FRAME_DELTA 0x1403c126c, GUI_LIST 0x143a13ac8, RETREAT_POINT 0x147fc7638,
RNG_SCENARIO 0x147fc6fdb, AIRCRAFT_SELECTOR 0x1403bd008, the INIT_* GUI
constants, etc.). Those are labels, not functions: a global-symbol port pass
would need its own anchor delta + xref-based matching and was not attempted
here.
