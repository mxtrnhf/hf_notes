## Result of the first ally run (hf_ally v0.2.0, campaign, log `Highfleet_2026-10-15_17-57-23.log`) [game]
* **It works mechanically.** Battle 1: `ALLY deploy returned 1, roster 1 -> 2, reserve 1 -> 0`, then `ALLY ready ... side=1 ai_flag=1 mode_d70=2`. The ally was a real second ship of the fleet, drawn from the reserve by the vanilla deploy function, side +1, AI on, wingman mode. Player report: it appeared, **flew away boosting upward, and fired a missile at an enemy**, so the stock AI tick runs and shoots for a mode-2 ship.
* **Only once per session (my bug, fixed in v0.2.1).** Battles 2 to 4 of the same session (player deploys at game time 44, 61, 98) produced no `deploy` or `no reserve` line at all: the "armed again" step waited for the tick to see an empty roster, but the battle manager stops being called when a battle ends, so the flag never reset. v0.2.1 re-arms when the player's own deploy happens at scenario selector 1 (the ally's deploy goes through the same call site at selector 2 and does not re-arm).
* **Wingman code exists in the AI tick** `FUN_140062f90`: it compares `+0xd70 == 2` at `0x140063396`, `0x14006391d`, `0x140063e3b`, `0x14006485c` (load), `0x140065e62` and `0x140065ef2` (the last two sit around the missile launch at `0x140065edb`). Read so far:
  * `0x140063396`: for a mode-2 ship it scans the global creature list (`0x143faa5d8`) for a **same-side creature (side product > 0, not an evac pod) whose `+0xbc4` is above 0.5** (constant at `0x1403527a4`) and sets a flag (`R12B`) when it finds one; that flag later skips parts of the target handling at `0x14006356c`. The scan does not exclude the ship itself, so with `+0xbc4 = 1.0` (what the deploy sets) the ally may count itself as the engaged leader [guess, unverified].
  * `0x14006391d`: for mode 2 with an empty launcher list (`+0x13d8 == +0x13e0`) it walks a list from `0x14006ee10` and compares heights (`+0x1844` against a body position +4): some "stay above / below" rule [not read].
  * `0x140065e62`/`0x140065ef2`: mode 2 reaches the Zenith launch path [not read in detail].
* The "boosted up" flight is not yet explained: it can be the stock attack run toward enemies that spawn above, or a wingman rule. v0.2.1 logs `ALLY track` once per game second for 25 s (ally and player position, the AI's waypoint at `+0xbf0/+0xbf4`, target, state) so the next run answers it.

## Result of the re-arm run (hf_ally v0.2.1, log `Highfleet_2026-10-15_18-06-48.log`): mode 2 is a strike run, not a wingman [game + code]
* Spawning across battles works (two `ALLY battle ... deploy returned 1` in one session).
* The `ALLY track` lines show the flight: in state 1 the ally closes on its target (waypoint a few hundred units ahead of it, ally moving about 100 units/s toward it); when it switches to **state 2** the waypoint is exactly **its own position + (+-1000, -1000)** every second and it flies off that way until the manager removes it. In battle 2 it was in state 2 from the first frame (target set, waypoint `pos + (1000,-1000)`, then `(-1000,-1000)`) and was gone from the roster 3 s later. The player's Discord guess matches: mode 2 is a leftover **bomber/strike-craft run** (one pass, then leave), and a missile-heavy ship "launched one missile and disappeared".
* Code behind it [code]: for `+0xd70 == 2` the missile-launch block of the AI tick (`0x140065e62`..`0x140065f0b`) looks the current target up in a global `std::map` at **`0x147fc7550`** (ship pointer to a float allowance) and launches only when the entry exists and its value is above zero (the value is then consumed); the target choice `FUN_140078b40` for mode 2 draws candidates from the same map (`0x140078bc5`), and when none is found the ship is put into state 2 (`ship+0xbdc = 2`) = leave. The battle manager `FUN_1402cc260` additionally removes idle mode-2 ships that are near the arena edge (`rep_1401f3c10_APP_MoveVolume(ship,0)`). So a mode-2 ship that is not in the allowance map has nothing to attack and exits. Also `ship+0xd60 = 2.0` (launch cooldown) is set after a launch in mode 2.
* Consequence: the ally must **not** be mode 2. `hf_ally` v0.2.2 adds `ally_mode` (default `0`, expected to be what the enemies use; the `ALLY battle` line now prints one enemy's `mode_d70` for comparison). Mode 1 is the player's own ship. The promotion of an ally when the player's ship dies does not need mode 2: the manager promotes `roster[0]` whenever no roster ship has mode 1.

## Result of the mode-0 run (hf_ally v0.2.2, log `Highfleet_2026-10-15_18-29-17.log`) [game]
* **Mode 0 is the enemies' mode** (`enemy mode_d70=Some(0)` in every battle). With it the ally stays in state 1 for the whole track (no peel-off), closes on its target and keeps fighting. Player report: a Navarin ally circled the enemy and kept firing; it did not use missiles or bombs in that fight, but in other fights allies "sometimes launch" while being "a lot less active than the enemy AI".
* **Across battles it works**: six battles in one session, including a 3-ship fleet (`reserve 3 -> 2`, one ally per battle by design).
* **Leaving the battle with the player's ship hands control to the ally** (`mode=1 ai_flag=0 dist=0` in the track), as the manager's promotion rule predicts. Side effect reported by the player: **a fleet with an ally has no way to retreat** (flying out switches ships instead of ending the battle). Idea, not built: when the controlled ship leaves alive (not state 6 or 7) and only AI ships remain, remove those too. The removal call has to be taken from a `CALL` operand in the 1.163 manager (the Ghidra label `rep_1401f3c10_APP_MoveVolume` is a 1.151 address and `0x1401f3c10` is the wrong place), which is not done yet.
* **The QoL AI mods do not cover the ally**: `ai_flares` and `ai_missile_dump` select "AI" ships by `side < 0`, the ally has side +1. Giving it flares and missile dumps means changing that test to "AI flag set and not the controlled ship" in the QoL fork.
* **"Less active than the enemy AI"** has no explanation yet. The launch gate in the AI tick (`0x140065d40..0x140065e53`) is bounds, range, cooldown and a 1% roll, with no side test in it. `FUN_140074220` (reload set-up) differs by side: for side > 0 the random reload delay is drawn from `(0,0)` instead of the AI range. Candidates are the difficulty/skill scaling that is applied to negative sides only, ammo choice, and the ship's own loadout. v0.3.0 adds a **paired probe**: for 60 s per battle, one `ALLY probe ally` and one `ALLY probe enemy` line per second (position, speed, state, target distance, aggression, control bytes, launch cooldown, Zenith and gun lists with loaded/reserve/ready counts), with launches and shots counted every frame for both ships.

## Result of the v0.4.0 retreat run (logs `Highfleet_2026-10-16_11-33-07.log`, `_11-37-21.log`) [game + code]
* **The F8 order works**: `retreat ordered (key)` sets mode 2 + state 2 on the ally; it flew to the arena edge and left (`track ended, still in roster: false`).
* **Auto-retreat via the same order does not work**: when the flagship left alive the order was logged (`flagship gone from the roster`, `retreat ordered (flagship left)`), but the next probe line shows the ally with **mode 1, ai_flag 0, state 2**, standing on the player's position: the manager had already **promoted it to the player's ship**. Reason, from the manager `FUN_1402cc260` (decompiled): when no roster ship has mode 1, it counts down the wave timer `0x147fc7020`, calls the deploy `0x1402d6e90` with slot 0 (so a ship left in the **reserve** is deployed as the new player ship when the timer is 0), and if the controlled ship is missing or in state 6/7 it sets `roster[0]` mode 1 and `SetLink`s it. Our hook runs at the start of that same call, so the order is overwritten. Only when roster and reserve are both empty and the timer is 0 does the battle end (result -1 or 2).
* **So a retreat needs the ally out of the roster before the manager's promotion**: v0.4.1 calls the extraction `0x14020ef30(ally, 0)` from the hook the frame the flagship is gone. Open: a third fleet ship still in the reserve is deployed by the same block (the log showed reserve 2 -> 1 after the ally), so with three ships the retreat may still be undone; to check in the next log (`ALLY retreat with the flagship` line prints roster, reserve and timer).
* Not duplicates: the log shows one `hf_ally` and one `highfleet_qol` (the first v0.4.0 launch also loaded `hf_funccall`, which bound F8 too; removed). The modloader line `Mod doesn't support game version: highfleet_qol.dll` appears in every log since 2026-10-14: that DLL's own version export, harmless (its 1.163 patches still install).

## Result of the v0.4.1 run and why a promoted ship cannot retreat [game + code]
* v0.4.1 (extract the ally the frame the flagship is gone): the retreat ended the battle for the whole squad, as in a one-ship fight (log `Highfleet_2026-10-16_11-49-37.log`). Extraction does not take the ally out of the roster at once (`roster 1 -> 1` right after the call); the manager's cleanup drops it a frame later.
* **How retreat works** [code]: the game keeps a **retreat point** in the globals `0x147fc7638` / `0x147fc763c` (two floats, an arena-edge point picked at random by `FUN_1402c9bd0`). The manager `FUN_1402cc260` begins by calling `0x1402cbc60(controlled ship)`: if the ship is within 1.5 x its radius of the point, it **zeroes the point** (one 8-byte write) and extracts the ship with `0x14020ef30`. A zeroed point means "no retreat", so **after the flagship has retreated, the promoted ally finds no retreat point**: that is the "Retreat: UNAVAILABLE" the player saw, and it has nothing to do with the roster.
* v0.4.2 adds `flagship_leaves`: `"retreat"` (v0.4.1, whole squad leaves) or `"handover"` (the ally is promoted by the game and the mod writes the saved retreat point back, so the new flagship can retreat too). Not yet run. **Run result (log `Highfleet_2026-10-16_12-08-11.log`) [game]:** `handover` works: both times the flagship retreated the log shows the retreat point going from `0x0` back to the saved value and the ally promoted (mode 1, ai_flag 0); the player confirmed retreat stayed available. Side effect seen: the player pressed the retreat key (F8) on the promoted ship, which forced mode 2 / state 2 onto a ship they were flying; v0.4.3 ignores the key on a ship that is player-flown. Still unknown: end-screen accounting (escaped or casualty) for an extracted ally.
* Multiplayer slot variants of the same logic exist (`FUN_1402cc7e0`, `FUN_1402cce70`, per-slot timers `0x147fc7020..`); not relevant here.

## Result of the v0.6.0 run: the ALLY toggle button [game], log `Highfleet_2026-10-16_13-47-48.log`
Screenshots (player): [pre-combat screen](img/bug_dupe_button.png), [combat screen](img/bug_dupe_button_combat.png).
* **The button is created and clickable.** Log: `ALLY toggle created c=... at (136,421) next to OK (21,421) size 274.3x154.3 active=2`; the click hook caught every click on it (`ALLY toggle clicked`). The element appears in the pre-combat screen as a second round crossed-swords button (the `precombat_button` sprite, a smaller copy of the OK ring), overlapping the "2. START BATTLE" plate. The position convention is confirmed: GUI coordinates are centre-based with y down (OK at (21,421) is the bottom centre of the 1920x1080 frame).
* **Bug 1, double toggle:** every physical click reached the click handler twice (the log shows `OFF`, `ON` in the same second, once three times), so the setting flipped back. Fix in v0.6.1: one toggle per 350 ms.
* **Bug 2, the leak:** after the fight started the button was still drawn in the middle of the combat screen: the game frees its own screen elements through its own lists, ours was never freed. Fix in v0.6.1: the element is hidden (active flag +0x48 = 0, the state the game uses for its own unused elements) when `PRECOMBAT_OK` / `PRECOMBAT_BACK` is clicked and again when a battle is running, and it is reused (flag set back to 2) when the screen is built the next time.
* The role icons of the beta exist as sprites: `order_unset`, `order_bombing`, `order_support` and their `_on` variants in `Media/Tex/Midground2.res`. v0.6.1 uses `order_support_on` / `order_support` for the toggle.
