# The two ship panels in battle (bottom corners), and how a mod could add more (1.163)

Status: **read statically (ds3-subview report, 2026-10-26; call sites, panel size and the target-link read re-checked in Ghidra by the curator, the rest is the agent's reading [agent])**. Run in game; the v0.14.9 fix was superseded by the v0.14.10 correction below. Tags: legend in `../README.md`. Report: the local `ds3-subview` report (523 lines, quotes the code). Screenshot labels from the user: the left panel is our ship, the right panel is the enemy ship that carries the yellow target box.

## What it is [code]
* **One function draws both panels:** `DrawBattleShipPanel` (`0x1402fde80`, old name `tacticalCombat?`, body to `0x140300518`). The battle renderer `0x1403050a0` calls it twice: `0x140309ab4` with `R8D = 2` (surfaces `[0x14800efa8]`, `[0x14800efe8]`) = **own ship, left**, and `0x140309b55` with `R8D = 3` (surfaces `[0x14800efb8]`, `[0x14800eff0]`) = **target, right**. The choice is a mode byte, not a ship pointer.
* **Mode 3 shows `playerCreature+0xb00`** (the ship's target link); a null link draws nothing. Any other mode shows the player's own ship (`Profile_GetPlayerCreature(profile, 0)`). A second player (co-op) halves the zoom and shifts the quads by +-87.5.
* **Gates outside the function:** the left call needs the HUD byte `[0x143a11961] != 0`; the right call also needs `[0x147fc6fca] == 0` (the same byte that gates the end-game, see [../findings/end-game.md](../findings/strategy/end-game.md)); `[0x143a15908] != 0` makes the whole pass return. A transient third path at `0x140309ab9`..`0x140309b31` draws into the right surface with another schematic function (`0x1402fa610`) and suppresses the target panel (not decoded).
* **Each panel is an offscreen 350 x 300 render target** (created at `0x1402e8c16`/`0x1402e8cb3`/`0x1402e8df3`/`0x1402e8e13` through HGE vtable slots `+0x300`/`+0x308`), drawn as a sprite at hard-coded corners by the caller: left `(0, H-300)` (or `(1545, 40)` when `[0x147fc6fd4] != 0`), right `(W-350, H-300)`; 1920 x 1080 gives `(0,780)` and `(1570,780)`. The composite runs before the pass in the same frame, so the sprite shows the previous frame's content. No mirroring: the right panel is the same drawing at the other corner.

## What is drawn [agent]
* **Text** (font `vcr_30`, scale 0.5, white; positions in panel pixels): timer `TADS_TADS` label at (30,15) and `hh:mm:ss` at (30,30) (`profile+0x360` seconds, a battle clock, same in both panels), `ON_FIRE_TADS` at (30,65) when `ship+0x1658 != 0`, ship name (30 chars wide, centred 175,230) and `KMH` speed (175,245) from `ship+0x1854/58`, counters top-right `ASM` (ПКР), `AAM` (РВВ), `GPB` (БМБ) at x 270, y 15/30/45, and bottom-right `FUEL` (ТОПЛ), `EVAC` (СПАС), `FSS` (ПОЖ) at y 230/245/260 (turn yellow `0xFFFF00` when low). Meanings of the abbreviations are guesses from the Russian labels.
* **Background:** `DrawNoiseHudOverlay` (`0x1402f7f00`, `(0,0,350,300)`) is called at the END, so the scanline noise covers text and schematic. `scaner_hud` is loaded but never drawn.
* **Schematic = the ship's real parts**, one quad per part body whose owner (`+0xb8`) is the panel's ship and which is not a Frame, walked through a 40-bucket body grid (`0x144094c88`, 40000 slots per bucket, parallel render records at `0x143faa680`). Per part: `Body_UpdateRenderTransform` (`0x14004dd50`) -> `SetShipZoom` (`0x14004ec80`) with the panel camera, colour, project (`0x1402e08b0`), draw (`0x1402e0cf0`, blend mode 6).
* **Colours** (flags = `*(int*)(GetStats(part+0x188)+0xb0)`): bit 2 white, else bit 1 light blue (105,172,240), else bit 0x10 yellow, else dark grey (51,50,45); which part category each bit means is not decoded (guess: armour / utility / special module; the yellow disc in the screenshot is a part with bit 0x10). **Damage** `d = hp/max (+0x2c8/+0x2cc)`: `R = (1-d) + d*R, G = d*G, B = d*B` (damaged white = pink, destroyed = pure red). **Burning** (`part+0x2f4 != 0`): `a = |sin(t*6)|`, blended toward orange `(1, 0.306, 0)`. A brightness lift (`fade = bucket/40`) is added last. **No icons**: only part quads, noise and text.
* **Scale and clip:** `ZOOM = min(140 / r, 21.000021)` with `r = ship+0x1850` (bounding radius), camera centre = ship position (`+0x1840/+0x1844`), panel centre (175,150); the ship therefore fills about 140 px in every panel. Clipping is by the render-target viewport, not a scissor rect.

## Adding more panels (allies, other enemies) [agent; feasibility, not tried]
* The function has **no ship, scale or position parameter**; its text, centre and size constants are fixed to 350 x 300. A smaller surface would crop, not shrink.
* **Recipe:** keep rendering into 350 x 300 surfaces and shrink at composite time with `FUN_140172aa0(sprite, x, y, rot, hscale, vscale)` instead of the plain blit `0x1401725c0`. To show another ship, save `playerCreature+0xb00`, write that ship, call `0x1402fde80(surfA, surfB, 3)`, **restore `+0xb00` at once** (the AI and targeting read it during the frame). Texts cannot be dropped per call (only by intercepting `displayOnUI_` `0x1401ae090` for your call); the simplest is to accept the full panel.
* **State:** the function saves and restores `ZOOM_LEVEL` `0x1403c11c4`, `TARGET_SCREEN_X/Y_` `0x148075ce8/cec`, both shake pairs `0x148075cf0/cf8`, the panel centre `0x14801fd10/14` and two per-part fields. It does NOT restore the bound render target (it leaves surface A bound), the player's `+0xb00`, or the sprite blend state; the caller must rebind its own target.
* **Hook sites:** wrap the two `E8` call sites `0x140309ab4` and `0x140309b55` (5-byte `E8` with no RIP-relative operand, trampoline per [../hooks.md](../hooks.md)), call the original first, then run your extra passes as complete units (bind your surface, draw, rebind the game's), then composite your sprites right after the game's own two blits (`0x1403090fc` / `0x140309151` area). Alternative: hook the function entry (mode in `R8D`) or the `MOV RDI,[RAX+0xb00]` at `0x1402fe0b6` (`48 8B B8 00 0B 00 00`).
* **Cost:** one scan of the body grid, one quad per part (100+ for a big ship) and 12 noise sprites per panel; four extra panels roughly quadruple the schematic cost. The game is single-threaded per frame, so sequential calls are fine.
* **Who is ally or enemy in the frame:** battle creatures are the 0x18-byte records from `0x143faa5d8` (creature pointer at `+8`, the list the AI chooser uses); side is the float `creature+0xad4` (positive = player side, ground defence is -1.0); skip `+0x48 == 0`, evac pods (`0x140074080`) and non-ships (`(+0x28 & 0x2f) == 0x2f`, `+0x1c0 != 0xd`).
* Open: which part category each flag bit means, the `[0x147fc6fca]` meaning, the transient third path, the 287 x 197 pair of surfaces (`0x14800efc8/eff8`, a third smaller HUD view not chased), the source of the HUD enable byte `[0x143a11961]` beyond `handleBattleBackgrounds`.

## Implemented in `highfleet-allies` (v0.14.4, corrected through v0.14.10) [code, in game]
`ally/src/ally_panels.rs` uses two private 350 x 300 target pairs and sprites, created lazily from the HGE `+0x300` slot and `hgeSprite` constructor. Two hooks:
* the own-panel call `0x140309ab4` renders each living ship in `ALLIES` with `0x1402fde80(myA, myB, 3)` after saving `player+0xb00`, pointing the link at the ally with native `SetLink` on `player+0xaf8` (v0.14.6) and restoring it at once. The following game call then draws the player's own panel into the stock left pair, so the two paths do not share surfaces.
* the panel-composite flush `0x14030915f` runs after the stock left/right panel sprites have been drawn, where the renderer is already in the sprite state, and draws the private sprites with `FUN_140172aa0` at scale 0.5. Two 175 x 150 panels sit at `(350, H-300)` and `(350, H-150)` and therefore appear one frame after their render, like the stock panels.

The earlier attempt reused the stock left surfaces and composited immediately after the offscreen render; that kept the panel function's offscreen renderer state and drew nothing visible. Hooks are installed only with `spawn_ally` and the `ally_panels` option; a live ally is required. Appearance was seen in the 2026-11-03/04 logs; the frame cost has not been measured.

**Follow-up (2026-11-03, in-game user report):** two rendering/lifetime corrections.
* The temporary target change must go through native `SetLink` `0x140194de0` on `player+0xaf8`, not a raw write of `+0xb00`: `SetLink` moves the link registration between the old and new node's link lists and refreshes `id`; a raw pointer leaves the old target's link list holding a link whose node now points elsewhere.
* `DrawBattleShipPanel` scans HUD marker layers 1..39 via the counts at `0x143a51160` and layer-1 owner field `0x144094c88`. The 2026-11-03 01:31 screenshot showed an ally panel containing text but **no ship parts** while the stock enemy panel was complete.

**Root cause of the missing ally schematic (2026-11-03, v0.14.9) [code]:** the HUD marker table is rebuilt from scratch every frame. `Creature_RecalcStatsPass` `0x140287370` (PreTask) zeroes the per-layer counts (`g_nHudMarkerCounts`, `0x143a51160`; 0x46 ints), then calls vtable `+0xb0` on every world body. For a `Body` that is `Body_UpdateHudMarkers` `0x14002d7b0(body, initialise)` (renamed in Ghidra 2026-11-03; old name `rep_14002e3c0_..._Xtime_get_ticks`):
* the first gate is the body vtable `+0x78` predicate = `Node_IsStateActive` `0x140005e60`, i.e. `node+0x48 >= 2` (0 is dead), then `body+0x8f8 > 0` (opacity);
* with `initialise == 0` it also requires the HUD-initialised byte `body+0x910 != 0`, otherwise it returns without registering anything;
* with `initialise != 0` it sets `body+0x910 = 1`, walks the body's sprite vector (`+0x8c0/+0x8c8`), and for each sprite with `sprite+0x128 != 0` writes a type-2 marker `{type=2, owner=body, index=sprite index, scale=1-0.05*step}` into the layer from `sprite+0x114` in the marker table (`g_pHudMarkerTable`, `0x143faa680`; 0x46 layers x 40000 records, stride 0x18), then recurses into the children through `Node_ChildCallB0` `0x140280010` with the same flag. The init byte is now `Body::bHudMarkersReady` (+0x910) in the Ghidra `Body` type.

The normal spawn path performs that `initialise = 1` call once; the mod's temporary ally deploy skipped it, so `body+0x910` stayed clear and the per-frame pass ignored every ally part forever. `Hud_RegisterMarkerForBody` `0x14011c760` is not a fix on its own: it forwards its own second argument to `Body_UpdateHudMarkers`, and v0.14.7 passed `0`.

The first v0.14.9 fix called `Body_UpdateHudMarkers(ally, 1)` before rendering an ally that had no markers in the current frame; v0.14.10 replaced it (see the correction below). That call used the same marker records, layers, scale and damage/burning palette as an enemy panel. A bounded synthetic-marker fallback (render body grid plus the creature part list, missing markers into layer 1) remains only for the case where native initialisation still produces nothing; it logs the part count, inactive count and the hp-ratio range, which also explains a red schematic (the panel blends towards red as `hp/hp_max` (`+0x2c8/+0x2cc`) drops).

**Correction (2026-11-03, v0.14.10) [code + game log]:** that call cannot work for a deployed ally. The in-game log line `ALLY panel c=0x1c64d930: native marker initialisation produced 0 part markers` (battle of the 2026-11-03 02:20 session) shows `Body_UpdateHudMarkers(ally, 1)` registering nothing, and the same happened for the previous player ship after a control handoff. The reason is the gate above: a deployed ally (and its parts, as far as the walk is concerned) is not in the state the function requires, and its child walk `Node_ChildCallB0` repeats the same state gate, so nothing below it is reached either. `Hud_RegisterMarkerForBody` `0x14011c760` forwards to the same function and fails for the same reason.

The panel therefore writes the type-2 records itself for the duration of its call. Two properties of the panel make the layer choice essential:
* `Hud_DrawChildMarker` `0x1402e08b0` draws only records with `type == 2`; type 1 (whole body) and type 4 (GUI) are skipped.
* the panel lifts a record's brightness by `layer / 40` (clamped to 1) and appends records layer by layer from 1 to 39, so the layer is both a brightness and a draw-order input.

Layer and scale of a part sprite, as `Body_UpdateHudMarkers` computes them: `base = clamp(4*m_floor(+0x9b8) + inherited stage, 0, 0x45)` where the inherited stage is `Body_GetInheritedStage` `0x140033b00` (own `+0x8d8` plus every Body ancestor's); `top = clamp(sprite stage (+0x114) + base)`; a sprite with bit 0 of `+0x50` also gets a record every four layers from `bottom = sprite stage - 4*floor + base` (0x3c instead of 0 when `base > 0x3b`) up to `top`; the scale is `1 - 0.05*(top - layer)`. v0.14.6-9 put every synthetic record in layer 1, which is why the ally panel showed a near-black hull with the modules standing out ("only parts are visible"): with `layer/40 = 0.025` the dark-grey palette gets almost no lift, and every module painted over the hull because all records shared one layer.

* The stock target panel is skipped while `0x147fc6fca` is non-zero; the ally panels now use the same gate, exclude retreating ships (`+0xbdc` 2), and clear cached panel content when no ally is rendered, so a texture cannot survive into the end screen.

The same battle HUD post-pass also hosts the ally target boxes (`ally_reticles`, v0.14.4) and the optional `debug_overlay` rings/state labels (v0.14.14-15); `ship_switching` (v0.14.5) takes the ship last shown in the top or bottom ally panel with keys 1/2. See the public `highfleet-allies` docs `ship-switching.md` and `debug-overlay.md`.
